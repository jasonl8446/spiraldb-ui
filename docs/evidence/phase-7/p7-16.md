## Criterion 1: the D69(h)/D77(d) family, one mechanism at a time

### F1: `a11y.spec.ts` "the server reads exactly the corpus on disk at the path it reports" (the 323-vs-322 count)

**Mechanism.** The arm reads the server's quest list, then counts `QuestTemplates/*.json`. Those are two readings of
the D17 clone taken at different moments. `p7-drafts.spec.ts` runs on another worker and saves a real quest file into
the clone, restoring it in `afterEach`. If a save lands between the two readings, the directory holds 323 files while
the list holds 322 rows.

**Deliberate reproduction.** A probe repeats the arm's body verbatim 400 times on one worker while `p7-drafts` runs on
another (`--workers=2`). Sidecar lines 478–532:

```
      3     Expected: 323
      3     Received: 322
  3 failed   [corpus arm copy 7, 12, 14]      <- inside the ~18 probe copies that overlapped p7-drafts
  403 passed (3.2m)
```

**Fix (D183 a).** A cross-process clone lock, `lockClone()` in `tests/helpers/clone-fixture.ts`. The mutex is a file
created with `wx`, and it records the holder's pid so a lock left by a dead worker is taken over. `p7-drafts` holds the
lock from its snapshot until its restore is verified (`beforeEach` → `afterEach`, released in a `finally`). The corpus
arm holds it across both of its readings.

**After.** The same probe, carrying the arm's post-fix body, again overlapped `p7-drafts` (drafts tests 2–18
interleave with the probe copies):

```
  406 passed (3.2m)      (sidecar line 1010)
```

After every run the lock file `data/.test-spiraldb.tier1.lock` is absent.

### F2: `a11y-keyboard.spec.ts` "extract → save: the dropzone button opens the file chooser with Enter" (1 min timeout)

**Reproduced under load** (unmodified spec, `--repeat-each=60 --workers=16`): **8 failed / 52 passed**, all at
`waitForEvent('filechooser')`. The failure snapshot shows the dropzone button `[active]`: it had focus and the
Enter was pressed.

**Mechanism, instrumented.** The probe logs keydown, click and `cancel` events. Every failing run looks like this
(sidecar line 484):

```
keydown Enter on BUTTON | click on BUTTON trusted=true | click on INPUT type=file | input cancel | keyup Enter
```

The input *did* open a chooser, a real headless one that cancelled at once, so Playwright's interception was not yet
in force. In playwright-core 1.63 (`coreBundle.js`), subscribing to `filechooser` calls `_updateSubscription`, which
sends `updateSubscription` **without awaiting it** (`.catch(() => {})`). `keyboard.press` is one protocol send with no
actionability round trips before it. So under `Promise.all([waitForEvent, press])` the Enter can reach the page before
`Page.setInterceptFileChooserDialog` does. `click()` never hits this race because its actionability checks come first,
which is why `extraction.spec.ts`'s click-to-browse arm is unaffected.

**Fix.** Subscribe first, then `await expect(dropzone).toBeFocused()`, then press. That puts one full round trip
between the subscription and the key. The assertion was already in the test; only its order changed.

**After.** The instrumented probe in its after shape passed 60/60 in three runs, with 0 `input cancel`. The fixed spec
under the same load passed **60/60** (sidecar lines 934–1333).

### F3: `extraction.spec.ts` Save All / Save Selected family (D77(d)'s "Save All lists the names…", p6-08's "…no overwrite wording…", p6-09's "Save Selected on a new quest…", p7-12's "a failed list read disables the Save All confirm", p5-06's "Save Selected saves only the selected quest")

**Mechanism.** Earlier runs recorded the call log (`final-verify-ui-runs.txt:534`): `performing click action` → `<li
data-sonner-toast data-type="info"…> intercepts pointer events` → 112 retries → 60 s. This probe measured the
geometry:

```
immediately after results: toast box=892,687 (still sliding in) | Save All centreHit=BUTTON
after ~1 s:                toast box=892,637 (settled)           | Save All centreHit=TOAST, Save Selected centreHit=TOAST
toast text = "Extracting quests... this may take a moment"
```

The info toast raised when extraction *starts* (5 s) outlives the extraction and settles over both result actions.
Unloaded, the first click lands while the toast is still sliding in. Loaded, the click comes later and the toast is
underneath it. A click that lands on the toast leaves the pointer parked there. sonner 1.7.4's toaster sets `expanded`
on mouse enter or move, and its timer pauses while `expanded` holds, so the toast never leaves and every retry is
intercepted.

**Deliberate reproduction** (the probe adds the loaded run's latency and parks the pointer on Save All's centre, as an
intercepted click leaves it; `--timeout=15000`):

```
[toast@12595ms] info:expanded=true   <- still up at 12.6 s; the 5 s duration is paused
  ✘ Save All asks for confirmation …                        (15.0s)
  ✘ Save All lists the names it would overwrite …           (15.0s)
  ✘ Save All shows no overwrite wording …                   (15.0s)
  ✘ a failed list read blocks Save Selected …               
  ✘ a failed list read disables the Save All confirm         
  5 failed / 3 passed        (the 3 passes first click a list option, moving the pointer off the toaster)
```

A control run with the latency but without the parked pointer passed, and every test took **5.6–7.6 s**: each click
waited out the whole toast.

**Fix (D183 b), in the product.** A user who clicks Save All within 5 s of results hits the same toast, so this is a
UX defect as well as a test hazard. `useExtraction` now keeps the notice's id and takes it down when the run settles:
results, failure, cancel, discard or unmount. `notifyInfo` returns the id and `dismissNotification` wraps
`toast.dismiss`, so the "one toast module" rule of `lib/notify.ts` still holds. `openResults` in the spec now asserts
the notice is gone (`toHaveCount(0)`).

**After.** The same parked-pointer probe on the product fix: **8/8**, each test 1.2–3.2 s instead of 5.6–15 s.
`extraction.spec.ts` + `a11y-keyboard.spec.ts`: 33/33.

### F4: `shell.spec.ts` "a nested route highlights exactly one item — itself, or the list item that owns it" (p6-09's `:747`)

**Reproduced under load** (`--repeat-each=80 --workers=20`): **4 failed / 76 passed**, all at the file's console
guard with `Failed to load resource: … 404`.

**Mechanism, instrumented** (the probe's fixture records every response ≥ 400): **10 failed / 70 passed**. Every
failure came from one of two unmocked reads on `/quests/DS-ACAD-C01-001`:

```
      4  404 GET /api/quests/DS-ACAD-C01-001/suggestions
      7  404 GET /api/status/quests/DS-ACAD-C01-001/history
```

The detail page starts both reads only after the quest document renders. Unloaded, the test finishes and closes the
page before either is answered. Loaded, the harness server's real 404 reaches the console guard. This is a hermeticity
gap (D40/D81), not a shell defect. Its visibility depends on timing, which is why it rotates.

**Fix.** `mockShellApi` mocks both reads, the same way every other read the page makes is mocked.

**After.** The same load: **80/80**.

### F5 (S1): `quests-goals-editor.spec.ts` "a pointer drag with the mouse moves a goal too" (the clipboard poll)

**Reproduced** (`--repeat-each=20 --workers=4`): **14 failed / 6 passed**, all at `copyPanelDocument`'s clipboard
poll, `Received: false`. It is not latency: `final-review-rereview.md` §S1 measured 60 s budgets failing the same way.

**Mechanism, instrumented.** The probe wraps `navigator.clipboard.writeText`, observes toasts, and times the Copy
click against the drop's mouseup. The results fall into two groups (sidecar `drag-probe2` section):

```
40-45 ms after the drag's mouseup -> NO writeText, clipboard empty   (13 runs)
45-57 ms after the drag's mouseup -> writeText called, clipboard "{" (7 runs)
```

The click reaches the Copy button, but the panel's handler never runs. In `@dnd-kit/core` 6.3.1,
`AbstractPointerSensor.handleStart` adds a capture-phase `click` listener that calls `stopPropagation`, and `detach()`
removes it with `setTimeout(removeAll, 50)`. So every click within about 50 ms of a drop is swallowed before React's
root listener sees it. When the reorder renders fast, the arm's Copy click falls inside that window, nothing is ever
written, and the clipboard poll cannot tell "not yet" from "never".

**Fix.** Two parts:

- **Criterion 2.** `copyPanelDocument` now waits on the panel's own success toast, "Quest JSON copied to the
  clipboard", and reads the clipboard once. The panel raises that toast only after `writeText` resolves. The toasts
  already on screen are marked before the click (`data-copy-seen`), so only a toast from *this* click counts.
- **The swallowed click.** After `mouse.up` the arm awaits an in-page `setTimeout(…, 50)`. `mouse.up` resolves once the
  page has handled the release, so this timer is queued behind dnd-kit's own 50 ms timer and cannot fire before the
  listener is removed. It is dnd-kit's own window used as the fence, not an arbitrary sleep.

**After.** `--repeat-each=20 --workers=4`: **20/20**. The whole file: 13/13.

**Negative control.** The fence was removed and the toast wait kept. Result: **9 failed / 11 passed**, every failure
`expect(locator).toBeVisible() … element(s) not found` at the toast wait (`quests-goals-editor.spec.ts:239`). A
swallowed click now fails fast with the right cause. The fence was then restored (the file is byte-identical to its
fixed form: `git diff --stat` 32+/12−, unchanged).

of a few `describe`/`it` titles changed, and no test logic.
