## Criterion 1 — migration 0005, `MIGRATION_FILES`, `db.test.ts` counts, spec

## Criterion 3 — rejected survives, accepted not re-proposed, only empty fields; CI runs the builder

`tests/unit/p7-drafts.test.ts` runs the builder on a **fixture catalog**. It is a `:memory:` DB seeded with 3
`quests`, 5 `quest_ids`, 2 gate refs, one zone and the strings those need, plus a temp SpiralDB root with 2 quest
files. It needs no fork, no clone and no WADs, so it runs in CI under `npm test`. Raw:

```
 ✓ … > the builder on the fixture catalog (CI) > proposes exactly the evidence each draft lacks, named and unnamed 9ms
 ✓ … > the builder on the fixture catalog (CI) > gives an existing file suggestions only for the fields empty in it 3ms
 ✓ … > the builder on the fixture catalog (CI) > proposes only values the shared schema accepts once applied at their path 5ms
 ✓ … > the builder on the fixture catalog (CI) > reconciles with coverage and gives identical counts on two consecutive rebuilds 5ms
 ✓ … > the builder on the fixture catalog (CI) > keeps a rejected suggestion rejected across a rebuild, and never resurrects it 5ms
 ✓ … > the builder on the fixture catalog (CI) > keeps a rejection when a sync links the named quest to a different id 4ms
 ✓ … > the builder on the fixture catalog (CI) > does not re-propose a value already accepted, from any source 7ms
 ✓ … > the builder on the fixture catalog (CI) > removes a pending evidence row once the file fills its field, and never touches decided or capture rows 17ms
 ✓ … > the builder on the fixture catalog (CI) > stores capture suggestions idempotently, and a rebuild keeps them 5ms
 ✓ … > the drafts and suggestions API (D141, D143) > rebuilds from the settings root and lists the ranked queue with the D130 toggle count 31ms
 ✓ … > the drafts and suggestions API (D141, D143) > answers 409 while a rebuild runs 57ms
 ✓ … > the drafts and suggestions API (D141, D143) > reads a draft's suggestions by name or id, and rejects once 15ms
 ✓ … > the drafts and suggestions API (D141, D143) > stores an extraction's capture suggestions when it answers (D161), keyed by the capture name 13ms
```

- **Rejected survives:** the test rejects a title, rebuilds, and finds 0 inserted with the same row still
  `rejected`. The second test covers a later sync that re-links the named quest to another id, which changes the
  identity, and the rejection still holds.
- **Accepted value not re-proposed:** after an accept, the same value is never re-proposed, even from a different
  source (a `capture-order` row accepting the same `m_requirements`).
- **Only empty fields:** a fully authored file gets 0 proposals. A non-empty `m_dialogList` blocks dialogue. A direct
  title already in the skeleton is not proposed. Filling the file's title and rebuilding removes that pending row.
- **Schema-valid values:** every proposal, applied at its path in path order, parses with `QuestTemplateSchema`.

restored (`diff` shows the file identical), and all 15 tests pass again.

## Accept helper (D141)

`acceptSuggestions(db, ids, draft)` in `server/src/services/drafts.ts` validates every id before flipping any: each
must exist, be pending and belong to the draft. A bad id is a `400`. It then flips all of them in one transaction.
It is **not wired** into `POST /api/quests` / `POST /api/quests/scaffold`, which is p7-08's job. The helper is
unit-tested through the accepted-not-re-proposed test.
