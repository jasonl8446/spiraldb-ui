## 2. The measured reality (1207 files) — everything the brief said, plus five things it did not

The brief's numbers all reproduce exactly: **1207 files, 0 unparseable**; three top-level keys in
1207/1207; `Events` present 1207/1207 and `[]` 1207/1207; **2365** Teleports entries, exactly
`{TriggerName, Teleport}`, string trigger names; nested objects exactly the six spec fields; **133**
scientific-notation `m_destinationLoc` values (every one with exactly one scientific component);
`TELEPORT_STATIC` in 2365/2365; **1205** distinct `ZoneName`s with exactly the two known duplicate
pairs; **1069** distinct destination refs, **1069/1069 resolving**, **36** with no transfer file of
their own; `zones` 1241 rows, 0 duplicate paths, 0 blank `display_name`.

Five measurements the brief did not carry, all now constants **and** asserted by the sweep:

1. **Top-level key order** is `ZoneName, Events, Teleports` in **1206** files; `ZoneName, Teleports,
   Events` in exactly **1** — `WizardZoneDatas_1-A.json`. A new document is not built by this editor
   (there is no create-by-UI), but the fact is recorded so the shape a save round-trips is the
   file's own (D5).
2. **The nested key order is not the spec table's.** The serializer order
   (`m_exitTeleporter, m_teleporterTag, m_teleportType, m_transitionID, m_destinationLoc,
   m_destinationZone`) appears in **2353/2365**; the L281-309 order in only **12/2365**. A newly
   added entry is built in the **majority** order and existing objects are **never reordered** —
   the lead confirmed this reading of D57.
3. **`serializeDoc` is byte-identical for 1206/1207 files.** The one exception is
   `WizardZoneDatas_Tutorial_Interior-A.json`, which ends with **two** newlines: its first save
   produces a whitespace-only diff, which the phase AC explicitly allows ("plus one-time formatting
   normalization"). **No** file lacks a trailing newline, so the normalisation is never the other
   direction. The no-op arm is therefore proven byte-identical on a real file *and* the one
   legitimate normalisation is named rather than hidden.
4. **`zones.display_name` and the existing `humanizeZone` do not fully agree**: **1172 agree / 69
   differ** of 1241 rows (**1010 / 59** restricted to the 1069 referenced zones). Every difference
   is a digit/letter boundary — the synced label keeps `DS_A1Z1` while `humanizeZone`'s
   `([a-z0-9])([A-Z])` rule splits it to `DS A1 Z1`. `formatNameRow('zones', …)` already prefers
   `display_name` and falls back to `humanizeZone` only for a blank label (0 of 1241), so the editor
   adds **no second humanizer**; both counts are constants so the day the synced data changes the
   sweep says so. (The brief asked to "confirm the two agree"; the honest answer is in this shape.)
5. **`entry_status` for `zone_transfer` is 1205 rows, all `extracted` — not 0.** The brief said 0.
   `server/src/services/import.ts` lists `{objectType: 'zone_transfer', directory: 'ZoneTransfer',
   keyField: 'ZoneName'}` in `IMPORT_TYPE_SPECS`, the first-startup import created them, and
   `GET /api/status/zone_transfers` answers those 1205 entries to match (live-verified). Task 4.10
   still owns the *UI* integration, but the rows already exist. `ZONE_TRANSFER_CORPUS.statusRows`
   now carries 1205 with this reasoning.

## 3. The blocking decision (the lead's reversal), stated once

The first implementation made the `m_destinationLoc` format finding a **warning** that could not
disable Save (the brief's original instruction, D73(a)'s machinery). The lead reversed it mid-story,
and the shipped behaviour is the reversal:

- the finding is `severity: 'error'`, `blocking === findings`, `warnings: []`, `blocked =
  findings.length > 0` (a `boolean` now — this family is a blocking family and the type says so);
- the page's Save gate is the shared `fieldHasError`, so a malformed location **disables Save** and
  `ObjectDetailPage` titles the button `"1 validation error blocks saving"` (L542-546);
- the reasoning is D65(a)'s severity-follows-the-corpus test: the rule has **zero corpus
  violations** (2365/2365 accept), so a blocking format rule **cannot block any real file** — it can
  only catch a value a user malforms in the editor, which is exactly what AC1 asks for. This is the
  opposite of an invented rule the corpus cannot exercise.
- **The converse is pinned in both suites** so nothing else became blocking by accident: an
  unrecognised `m_teleportType` and an unresolvable `m_destinationZone` each produce **0 findings**;
  a clean document is `blocked: false`; the engine's only finding kind is the format check; and no
  **reference** rule exists in either direction (1069/1069 references resolve — a rule would be copy
  with no surface).

## 4. Reuse decisions (generalise, do not fork)

- The **nested-object field model** lives in `shared/simpleObjects/zoneTransfer.ts`, beside the
  other five families' vocabularies, and extends that module's two shared types
  (`SimpleNamesType` gains `'zones'`; `SimpleFieldKind` gains `'zone-teleport-list'` and
  `'zone-select'`) rather than starting a parallel one. This is Phase 4's **first nested-object
  repeater**, so `readTeleports`/`TELEPORT_KEYS`/`newTeleportTriggerEntry`/`removeTeleportEdit` are
  the shapes the next nested family should extend.
- **A single zone value is `FriendlyNameDropdown`**, not `ObjectIdMultiSelect` — the multi-select is
  for lists (p4-03/p4-04), and using it for one value would be D71(i)'s mistake in reverse.
- **The label is the names type's**; the editor derives none (AGENTS.md rule 2).
- **The filename is `fileNameFor`**, asserted through `createNameFor`; nothing hand-builds `_`.
- **The generic pages are reused as-is**: `/zone-transfers` is `ObjectListPage` and
  `/zone-transfers/:name` is `ObjectDetailPage`, with the validation supplied as a module-level
  function. No page component of its own — the p4-05 reason for one (a hook injecting the synced
  table) does not apply, because this family's single rule consults no table.
- **The `validate` seam is client-only for this family**: `server/src/routes/objects.ts`'s optional
  `validate` is taken by DropTable alone, so a direct `POST` with a malformed location is not
  rejected server-side. Stated, not blurred (the p4-05 claim split, unchanged).

## 5. How the page resolves its key (the 1205-vs-1207 collapse)

The route carries the `ZoneName` itself, URL-encoded (`/zone-transfers/WizardCity%2FWC_Hub`);
`displayKeyFor` returns a **text** family's key verbatim (no ulong canonicalisation), and the server
resolves it through the D19 content-keyed index. Two keys are carried by two files each
(`WizardCity/Tutorial_Exterior`, `WizardCity/Tutorial_Interior`), and the index collapses them to
one entry — which is why `/api/zone-transfers` answers **1205** rows for 1207 files (live-verified,
with both duplicates reported in `duplicate_keys`, which the list page's corpus notice renders). A
save therefore reaches the one file the index resolved; **the second file behind a duplicated key is
not separately addressable from the list**, and this story states that rather than inventing a
disambiguator (the p4-01/D69 collapse contract, unchanged).

**The one case the lead tried to break it with is TOLERATED, deliberately**: `"1,2,3,+4"` is accepted. A leading `+` is not JSON-number syntax, but it **is** accepted by the .NET float parser this game data passes through, and the corpus contains **none** (0 of 2365). Tightening it would risk rejecting a legitimate value — the same reasoning that forced the scientific-notation arm — so it is **recorded as float-tolerance, not fixed**. The lead's initial expectation (reject) was the wrong side of that judgement, and the spec now pins the tolerance so a future change to it is visible.
