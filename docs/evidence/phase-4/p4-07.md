## 2. Decisions this story makes (for the lead's D-record)

1. **`/global-registry` is the editor, with no list and no detail route.** docs/spec-api.md **L474**
   says verbatim `/global-registry → GlobalRegistry editor`, the spec's route table lists no
   `/global-registry/:key`, and §4.9 / L711-712 say "a single merged view" — so the family that is
   one dictionary does not get the list→detail shape of the seven collections. The family's **list**
   endpoint is still consumed (by the page's disclosure), and the tier-1 spec mocks both endpoints.
   *The first implementation added `/global-registry/:key` and failed the pinned
   `tests/unit/ui-shell.test.ts` route-table assertion; the route was removed rather than the
   assertion relaxed.*
2. **The unkeyed family's read is the merge, and the route key is a name, not a selector.** Any key
   resolves while at least one file exists (a stale bookmark survives consolidation); no file at all
   is a 404 (the create path, not an empty registry). `resolveObjectPath` lost its old unkeyed stem
   branch so there is **one** resolution rule per family shape.
3. **A file the merge did not account for is never deleted.** Unreadable text, a non-object
   document, or a document with no `GlobalRegistryValues` is left on disk and named in the save's
   `warnings`. This is the named failure mode ("deleting a file the merge did not account for"),
   and it also keeps AC2's "exactly one file" honest: on the measured corpus the one file *is*
   accounted for, so the claim holds where it was measured.
4. **The unkeyed family skips the D45(1) merge on an update.** Its document *is* the whole
   dictionary, so the posted object is written verbatim — `mergePreservingAbsent` would resurrect a
   row the user removed, because this dictionary's "absent" is an absent **key**, not a null.
   Recorded as a phase transition in `tests/unit/save-pipeline.test.ts`.
5. **`outcome` stays `created` while `action` is `update`** on the consolidation save (the
   convention file did not exist; the entry did). Both fields are on the wire, so the pair is
   stated in the unit test, the live transcript and here rather than quietly collapsed.
6. **Edit/Save for a lifecycle-free family is an explicit prop** (`ObjectDetailLayout.editable` /
   `ObjectDetailPage.editable`, default `status !== null`), not an inference from
   `objectType === null` — so a future unkeyed family cannot silently become editable.
7. **A renamed row moves to the end of the table.** `shared/document.ts` has no key-reorder
   operation, so a rename is delete-then-set; documented in the model and in the form, and harmless
   because the consolidation writes a **new** file (no pre-existing file's order is disturbed).
8. **A rename commits on blur/Enter, not per keystroke** — the row's identity *is* its key, so
   per-keystroke renaming would remount the row and drop focus.

## 5. Honest limits

- **The live corpus has one file, so "later files win" is proven by fixtures only.** The live run
  proves the *commit*; the merge order is a unit claim with a real end-to-end read on a two-file
  fixture (`tests/unit/objects-api.test.ts`), labelled as such in both places.
- **The merge order is the tool's choice, not Imlight's.** Imlight enumerates
  `Directory.EnumerateFiles` unsorted (D22's rationale), so no order can reproduce it; the tool
  makes one deterministic order (ascending by name) and the consolidation removes the ambiguity
  that made the question matter.
- **A file that appears between the client's load and the save** is merged at save time (so it is
  accounted for and deleted). The posted document is authoritative for *values*; a key that only
  the new file carried would not be in the written file. A single-user local tool has no concurrent
  writer, and the honest mitigation here is the "accounted for" rule, not a silent guess. Stated as
  a limit rather than tested against a race.
- **Git's rename detection** displays this commit as `R088`; the tree is an add + a delete, proven
  with `--no-renames` from the same commit object. A future reader who runs `git show --stat` first
  will see the rename arrow, not two lines.
- **The clone's reflog retains the two probe commits** (git keeps unreferenced objects); no branch
  references them after the restore, and the working tree/branch/`main` are byte-identical to the
  pre-state.
- **`main` in the clone was moved by the first rig attempt** and restored to `f3f8b5c` (the gate-2
  fixture commit) from the reflog; the second run captured the pre-state and restored all four
  values (branch, HEAD, `main`, commit count).
- **An unknown key does not 404 for this family** (decision 2). That is a deliberate semantic
  difference from the seven keyed families, where a key *is* an identity.
