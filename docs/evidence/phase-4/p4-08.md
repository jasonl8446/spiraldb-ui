## 2. THE DEFECT THIS STORY FOUND IN p4-02's WORK (and the fix), reproduced by the lead

The per-type AC2 arm — which drives the real `POST` route with the **client's own body shape** — failed for `drop_table` at the edit step: **`ObjectDetailPage` never sent the save envelope's `key`**, and the server's DropTable validator identifies the entry being saved by `body.key` (forgiving exactly that corpus occurrence). Without it, `otherDropTableNames(keys, null)` includes the entry's own name, so **an unmodified save of an existing DropTable answered 400 "already used by another drop table"**.

Nothing had caught it because **every tier-1 spec mocks the POST 200** and p4-02's route-level tests supplied `key` themselves — so the client's actual body never met the real validator.

**The lead reproduced both sides end to end** (a fresh-port rig on a DB copy, the clone as the write target):

```
unmodified save WITHOUT key (the old client body) -> HTTP 400
  {"Name":["The name \"DS-ACAD-C01-001\" is already used by another drop table. …"]}
the SAME body WITH key (what the fix sends)        -> HTTP 200
  {"outcome":"updated","action":"update",
   "commit_message":"spiraldb: update drop_table DS-ACAD-C01-001",
   "file":"DropTables/droptables_ds-acad-c01-001.json"}
```

The fix is one line (`key` omitted for the unkeyed `globalregistry`, whose POST rejects a supplied key, so p4-07's path is untouched) plus the single whole-body tier-1 assertion that pinned the old shape. **The lead confirmed keeping it**: an unmodified save answering 400 is a user-facing defect, and AC2's "edits do not change status" is only true if the edit succeeds.

**Recorded as the episode's lesson (D76(a))**: an AC that depends on a real server path needs at least one arm that drives the **client's own body** through the real route — mocking the POST and hand-writing the body in a route test is exactly the blind spot that let this ship.

## 5. The one flake, attributed — and one poll made patient

The **lead's** first full `test:ui` run failed `tests/ui/status-integration.spec.ts`'s AC1 refetch assertion. That arm was **already** `expect.poll(...)`, so it had not *missed* a wait — it had **timed out** at the configured 10 s while this family's detail page (which reads the 317-row corpus list itself for its duplicate-name rule) queued behind many parallel workers. ## 6. Clone hygiene — and the axis D75(i) missed

The lead's defect probe **wrote** to the clone (the 200 arm), so it was restored — and the restore exposed a fifth axis: `git reset --hard <sha>` restores a **commit**, not the **checked-out branch**. The copied DB carried the developer's stale `git_branch: content/2026-09-26`, the save pipeline checks out whatever that setting says, so the probe's commit landed on `content/2026-09-26` and the reset moved *that* branch. Content was never wrong (both dated branches are at `18dc924`), but the checked-out branch was. The lead checked out `content/2026-09-27` again and verified:

```
clone: branch content/2026-09-27 | HEAD 18dc924 | main f3f8b5c | 42 commits | porcelain 0
       (content/2026-09-26 also at 18dc924 — harmless, the probe's branch)
fork:  main c55ccab | porcelain 0
```

**Recorded as D76(b)**: restore **five** axes (checked-out branch name, HEAD, `main`, commit count, porcelain), and a rig that may save must **clear or correct the `git_branch` setting** in its DB copy, because the pipeline honours it.
