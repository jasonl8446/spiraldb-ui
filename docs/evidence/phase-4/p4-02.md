## 3. Measured corpus reality this story rests on

- **317 files.** `Name, Description, RollChance, Weight, NoneChance, PityCounter, MinGold, MaxGold, ExperienceAmount, TrainingPoints, Items` are in **all 317**; the audit quartet is in **316** — and the one file without it (`droptables_wc-unicorn-side-001.json`) carries **none** of the four, not a partial block; **`GrantsPotionSlot` is in only 35**. So the form must be **presence-preserving (D57)**: a control for an absent key produces no edit, and the Audit section renders the quartet **even when absent and never writes it** (D69b).
- **All four rules have zero corpus violations** (317 distinct non-empty names, every chance within 0–1, `MinGold ≤ MaxGold` everywhere), so the negatives are fixtures and the story says so.
- **72 item rows**, each with **exactly** `ItemId, ItemName, Notes, Requirements`; **65 requirement leaves**; and **7 of the 72 rows carry `Requirements: null` explicitly** — which is what makes the shared tree's absent-slot path load-bearing for AC2.
- **The ItemId trap**: all 72 ids are JSON **strings** and resolve **64/72 numerically but 0/72 as raw strings**, with 8 genuine misses (`1000, 533943727, 534093744, 878360657, 927448295, 975200773, 1627273980, 1730822561`; `1000` is from `droptables_test.json`).

## 6. Decisions (D70)

- **The family validator runs before the generic key resolution on the server.** `Name` *is* the key, so the generic "no usable key" check would otherwise answer 400 **without** the D65 field map — i.e. the AC's own empty-Name arm would have had the wrong shape. With the engine first it returns "DropTable validation failed with 1 validation error (Missing name)" plus `fields.Name`. No other family has a validator, so their order is untouched (the p4-01 route tests stay green).
- **The duplicate rule's identity is `body.key`** (the route key), so an unmodified save does not reject itself — proven by the NOT-400 arm.
- **A null requirement slot creates a typed wrapper** (`$type: RequirementList`, as the shared `initializeTreeEdits` does and as 307 of the 314 corpus wrappers carry); only a **pre-existing untyped** wrapper stays untyped. This corrects the lead's brief, which said "the same untyped wrapper shape" for item `Requirements` — true of the 65 existing trees, not of a newly created one.
- **An unresolvable id does fire one `GET /api/names/items/:id` fallback** (which 404s and leaves the raw id): the "0/72 raw-string matches" trap is proven by the 64-vs-0 sweep in the model test, not by a zero-lookup assertion. This also corrects the lead's brief.
- **`object-editors.spec.ts` (the plan's single filename for AC#13-14) is deliberately not created here**: coverage is split across p4-01's `object-list.spec.ts` (NpcInventory) and this story's `drop-table-editor.spec.ts`, and **task p4-10 owns that exact filename** — so it will exist by the time the criterion's "≥2 representative types" is judged.

## 7. Flagged, and the rig lessons

- **A rename to a fresh name is still a create** under the generic router (the key comes from the document, so the old file stays). The duplicate arm — renaming *onto* an existing name — is blocked both client-side and server-side. A true rename flow would also need `entry_status.object_key` re-keying, which the save pipeline does not do; worth a decision if the owner wants renames.
- **If the client's `GET /api/drop-tables` list fetch fails, the duplicate rule injects nothing and skips**; the server still 400s. Documented on `DropTableValidationOptions.otherNames`.
- **Entering Edit mounts `useNames('items')`** (79,835 rows, sharing the dropdowns' query key); view mode fetches nothing.
- **Rig lessons this round (both discovered the hard way, and both are mine)**:
  1. **The D38 identity gate precedes validation on the POST path**: with no `user_name` every save answers **500** ("settings.user_name is empty"), so the validation field map is unreachable. A POST-capable rig must seed the identity as well as the clone path — and the settings endpoint is **`PUT /api/settings`** (a `PATCH` 404s), with the server reading settings **at startup**, so seed before boot.
  2. **Stale server processes accumulate across rounds.** My first live proof hit a server started in an **earlier round**, which predated p4-02's validator: it answered **200** for the invalid payloads — and because a 200 means a write, it left **two commits in the clone**. I restored it (`git reset --hard 18dc924`), killed **four** lingering `tsx server/src/index` processes (two from earlier rounds), re-verified no listeners, and re-ran the proof on a fresh server — which is why §5 is trustworthy. The rule for future rounds: **start every rig on a fresh port and assert the running server's identity before trusting a single probe**, and never leave a rig alive across rounds.
