Tier 1 mocks `/api/settings`, `/api/extract/quests` and `/api/quests`. The following are therefore
**not proven** and must be covered by the lead's tier-2 browser run with the real CLI, a real
capture and the real SpiralDB clone:

   (real `m_goals[]` with corpus NAMES, D48(a)), and the 413 upload-cap message with a real
   >512 MB file.
2. **D9/D47 for real** — that aborting the request really kills the CLI child via `res.on('close')`
   and cleans up its temp files. Tier 1 proves the *client* half (the signal and the visible
   return to upload) only.
3. **The real save** — files written to `QuestTemplates/`, the companion `QuestMetadatas/` update
   (paired by the `Name` field, D19/D20), the git commit and `status: extracted`. Tier 1 asserts
   only that the client POSTs `{quest}` and reads the documented response envelope.
4. **The real 409 dirty tree and the real duplicate-metadata warning** — tier 1 replays the
   documented bodies, not the server's own generation of them.
5. **The identity gate against real settings** — that a fresh SQLite database really has a blank
   `user_name` and that the gate's PUT persists (tier 1 uses a mocked settings map).
6. **Screenshots and visual fidelity** at both widths, including real 375px mobile emulation
   (tier 1 sets a 375px viewport, but it is not a device).
7. The D-40 harness itself is exercised only for this new page; nothing else changed.

## 4. Deviations from the spec copy, and spec-internal contradictions

1. **The format line contradicts the mockup.** `docs/spec-ui-design.md` L199 (mockup) reads
   "Supported format: JSON packet capture (.json)"; `docs/spec-domain-reference.md` L625 and
   `p2-07-ac1` require "Supported format: JSON packet capture files (.json)". The AC and the
   domain reference win — the longer wording is implemented and asserted. The literal is
   duplicated in `server/src/routes/extract.ts` (its `UPLOAD_FORMAT_HINT`) because the client
   tsconfig cannot import server modules; the server's copy is asserted by `tests/unit/extract-api.test.ts`.
2. **The action bar is the results footer, not part of the right panel.** Spec L226 groups Save
   All / Save Selected / Discard under the right panel. On mobile the right panel is not mounted
   at all, so an action bar living inside it would be unreachable at 375px. It is rendered as the
   results-level footer instead; the labels are the spec's verbatim.
3. **Confirm-dialog internals are invented** (title `Save to SpiralDB`, buttons `Cancel`/`Save`).
   Only the sentence is spec-fixed; the spec gives no dialog title or button copy.
4. **One success toast per quest.** `Save All` with N quests emits N toasts (the spec's only
   success copy is the per-quest `Quest {name} saved and committed`). A "Saved N quests" summary
   would be invented copy; sonner stacks at most 3 at a time and scrolls the rest.
5. **The upload error toast repeats the inline message.** The spec defines no upload-failure copy,
   so the server's own message is used both inline (`role="alert"`) and as an error toast.
6. **`Save All` stops at the first failure.** Remaining quests stay unsaved and retryable; the
   spec gives no partial-failure copy, so the ordinary error toast is used.

## 5. Spec-silent states — what was chosen

1. **Discard** (spec names the button, never its behaviour): clears the results *and* the file and
   returns to the upload phase, with **no** confirmation. A confirmation for a discard would be
   invented UI; nothing has been written at that point, so there is nothing to lose.
2. **Cancel** is the same state transition as Discard (abort + reset). Cancel is the only one
   offered while extracting, Discard only once results exist.
3. **Error state**: return to the upload phase with the drop zone usable again, an inline
   `role="alert"` line carrying the server's message, and the error toast. The alternative
   (staying on the file card with the error) was rejected as the more surprising of the two.
4. **Mobile breakpoint** is Tailwind `md` (768px) via `useIsMobile`, not a spec value (the spec
   only says the list takes full width). The 375px check is the AC's; the desktop pane needs
   ~640px+ to be useful next to a 320px list.
5. **The `new` badge persists after a successful save.** The client cannot know a quest is now in
   SpiralDB without re-listing (p2-08's endpoint), and the spec does not define a post-save row
   state. Deliberately left `new`.
6. **No `notes` is sent with a save.** `POST /api/quests` (docs/spec-api.md L253-258) documents
   only `{quest, notes?}` with no capture context, so the plan's "Imported from packet capture
   {filename}" history note cannot be expressed by this flow — see §6.2.
7. **The identity gate runs after the Save All confirmation, not before it.** Confirming the write
   is the more important modal; the gate then blocks the actual POST. Dismissing the gate is
   silent (no toast) because the user just cancelled.
8. **`notifyWarning` and `TOAST_WARNING_DURATION_MS` are p2-07 additions.** The design spec fixes
   only success/error/info, but `SaveQuestResult.warnings[]` (D48(d)) has to be surfaced as
   something other than a red error. The warning toast is 10s. `TOAST_DURATIONS` was deliberately
   left at its exact three-key shape — `tests/unit/ui-shell.test.ts` asserts that shape and the
   spec fixes it.
9. **The results pane has a definite height at md+** (`md:h-[70vh]`, `overflow-hidden`, both sides
   scroll internally) so a long quest cannot push the action bar off-screen. The value is
   spec-silent.
10. **`QUESTS_QUERY_KEY` exists even though the quest list endpoint is p2-08's** — the save
    invalidates it now so the future list is correct by construction.

## 6. Proposed follow-ups (for the lead to record as D-items / later stories)

1. **Per-overwrite confirmation (plan 2.4 L49) is not implementable in p2-07.** The UI cannot know
   which extracted quests already exist in SpiralDB without a list/index read (p2-08). Tier 1
   proves the save runs; whether it creates or overwrites is only visible in the server's
   `SaveQuestResult.outcome`, which the UI currently does not surface per row. Either surface that
   result in the results list or add the confirm in p2-08.
2. **The capture filename cannot reach the saved entry's history.** Plan 2.4 L48 wants
   "Imported from packet capture {filename}" recorded; `POST /api/quests` has no field for it.
   Options: extend the endpoint with an optional `notes`-style capture context, or drop the
   requirement. Worth a decision before p2-08 builds on the save flow.
3. **`docs/spec-ui-design.md` L199's shortened format line should be corrected** (or annotated) so
   the next implementer does not copy the mockup string; the domain reference and the AC are the
   contract.
