### 9.2 Gap B — the capture note (plan §2.4: note "Imported from packet capture {filename}")
The client's real POST body was captured with a route handler:
  [{ keys: ["quest","source"], source: "WC-UNICORN-MAIN-004.json", questName: "WC-UNICORN-MAIN-004" }]
=> the client half already worked. THE FIRST LIVE SAVE EXPOSED A SERVER DEFECT that no unit test caught:
  $ node -e "... select old_status,new_status,notes,changed_by from status_history ..."
  [{"old_status":null,"new_status":"extracted","notes":null,"changed_by":"Lead Verify"}]
  notes === the spec text: false
Root cause: savePipeline applied the note only when the JSON FILE was new (`outcome === 'created'`). An
extraction of an existing corpus quest — the normal case, 322 quests already exist — is a file UPDATE plus a
first-time `entry_status` INSERT, so it wrote no provenance. The rule was corrected to key on the
**entry_status insert** (the entry's first appearance in tracking), leaving D49(d) intact for already-tracked
entries. Tests were added that fail on the pre-fix code (5 new: 721 unit tests total).
RE-MEASURED LIVE after the fix, on a fresh tracking database, through the same real UI path:

                    "notes":"Imported from packet capture WC-UNICORN-MAIN-004.json",
                    "changed_by":"Lead Verify"}]
