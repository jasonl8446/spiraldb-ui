--------------------------------------------------------------------------------
THE DEFECT (measured live, re-measured here)
--------------------------------------------------------------------------------
Saving a quest that ALREADY EXISTS in the corpus through POST /api/quests with a
valid `source` produced an entry_status row inserted as `extracted` whose history
row had `notes: null`:

  status_history: [{"old_status":null,"new_status":"extracted","notes":null,
                    "changed_by":"Lead Verify"}]

Cause: savePipeline applied `historyNotesOnCreate` only when the FILE outcome was
`created` (`outcome === 'created'`). An existing corpus file saves as
`outcome: 'updated'`, so the note was dropped even though the entry itself was
appearing in tracking for the first time.

--------------------------------------------------------------------------------
THE RULE IMPLEMENTED (plan §2.4; docs/spec-api.md L122)
--------------------------------------------------------------------------------
The note is written when the save INSERTS the `entry_status` row — the entry's
first appearance in tracking — regardless of whether the JSON file already existed:

  | file outcome      | entry_status row | note                                  |
  |-------------------|------------------|---------------------------------------|
  | created           | inserted         | Imported from packet capture {source} |
  | updated (live case)| inserted        | Imported from packet capture {source} |
  | created / updated | already existed  | no note, no status reset (D49(d))     |

An update of an already-tracked entry still touches nothing: no note, no status
change, no history row. A reviewed/verified status is never reset.

Implementation (smallest correct diff, no public shape break):
  * `upsertEntryStatus` now returns `{ entry, created }` — it reports whether THIS
    call inserted the row, so the fact is known where the write happens and is never
    re-derived from the file outcome.
  * Its input gained `notesOnCreate` (the initial-row note) next to `notes` (the
    transition note for an already-tracked entry). The insert branch uses
    `notesOnCreate ?? notes`; the existing-row branch still uses `notes`.
  * The call site passes `notes: request.historyNotes` and
    `notesOnCreate: request.historyNotesOnCreate ?? request.historyNotes` — so the
    old `historyNotes`-on-create behaviour is preserved verbatim, and a create with
    only `historyNotes` still records it.
  * `SaveObjectResult` gained `statusCreated: boolean` (additive; the route's
    response shape is unchanged) so the rule is observable and testable. Always
    `false` for a family with no lifecycle (GlobalRegistry).
  * `historyNotes` (the non-create variant) behaviour is unchanged.
