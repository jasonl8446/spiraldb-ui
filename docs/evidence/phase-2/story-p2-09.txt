## decisions (the spec-silent points this story had to settle)

1. **The transition lives in the two spec locations, and deliberately NOT on the extraction
   results list.** Task 2.8 asks for the browse table's Actions menu (spec-ui-design L262) and the
   detail header's buttons (L281); the extraction results list is a *third* surface that the spec
   never asks for, and it is structurally wrong today: an unsaved extraction has no `entry_status`
   row, so by D51(f) a PATCH there would be a 404 by construction. Rather than ship a button whose
   every use fails, the action appears on browse/detail the moment a save has tracked the entry
   (the save path already invalidates the quests list, so it appears with no extra wiring).
   **Flagged for the lead:** if the results list should eventually offer it, that is a D-item
   (the endpoint would have to track-and-transition in one call). The mobile card list carries no
   action either, which matches the spec's four-field card (L270) — the Actions column is a
   desktop-table concept.
2. **A Radix `Popover`, not `role="menu"`.** D39 vendors only the primitives real code first
   needed; there is no dropdown-menu primitive. Two labelled buttons in a popover is honest;
   claiming menu semantics without the arrow-key roving focus the pattern requires would not be.
   Escape, outside-click and focus return come from Radix; the trigger carries a native `title`
   because there is no tooltip primitive either (the D51(b) pattern).
3. **Both the trigger AND the portaled content stop click propagation — found by the spec, not by
   reading.** Radix portals the popover to `document.body`, but React still bubbles the click
   through the **React** tree, where the popover is a descendant of the table row: the first tier-1
   run choosing "Mark Reviewed" also activated the row and navigated to the detail page. The
   trigger had a `stopPropagation` from the start; the content needed one too
   (client/src/components/quest/StatusMenu.tsx:76-86). This is the one real defect the story's own
   tier-1 specs caught.
4. **Both actions are always listed; the entry's own status is `disabled` and marked "Current".**
   The menu then also answers "what status is this row in?", and the AC's "disable or omit the
   action for the current status" is met by disabling (omitting would make the menu's contents
   depend on invisible row state). The header buttons use the same rule with the D51(b)
   `aria-disabled` + `title={Already <status>}` pattern the disabled Edit button established.
5. **The identity gate runs before the dialog, not merely before the request.** `requireUserName()`
   is awaited first and only then does the notes dialog open ("fires first" read strictly): the
   user is asked who they are once, not asked to click "Mark Reviewed" a second time afterwards.
   Cancelling the gate aborts the whole transition — no dialog, no request, no toast (asserted).
   `ExtractionPage`'s call site is the reference and `requireUserName`/`UserNameCancelledError` are
   reused verbatim, never re-implemented.
6. **A failed transition keeps the notes dialog open** with an inline `role="alert"` carrying the
   server's own message and the notes text still in the field (one click to retry); there is no
   duplicate error toast. Success closes the dialog and toasts `<quest> marked <status>`.
7. **404-vs-everything-else is the mapping, not the message text.** `ApiError` with `status === 404`
   is D51(f)'s untracked entry and becomes an actionable "save or import it first" sentence (two
   wordings: the dialog's, and the history panel's); every other failure passes the server's own
   message through via `serverMessage(error, fallback)`. Matching on `error.message` would break
   the moment the server rewords its body.
8. **The PATCH body omits blank notes entirely** (`{status}` only — never `notes: ''`), and never
   contains `changed_by`: the server attributes the change from the persisted `settings.user_name`
   (D37). Both are asserted exactly (`toEqual`).
9. **The optimistic write goes into the browse list's cached payload, summary included.** D51(e)
   makes the list row the single status source for both pages, so the mutation rewrites that row
   and recomputes the payload's own `summary` — the filter tabs' count badges stay consistent with
   the row's dot during the window. The settle invalidates the list, `['status']` and the history
   key; a failed mutation restores the exact previous payload (no partial rollback).
10. **The timeline's key and action are inline text with a real space** (not flex + `gap`), so the
    rendered text content is the spec's own line `DS-ACAD1-C01-001 marked verified`: a screen
    reader or a copy-paste gets the space, and the words are assertable as one string.
11. **`git_branch` is a read-only information row (D42), and the tension is real.** spec-data-model
    L206-214 describes it as generated (`content/YYYY-MM-DD`, created from `main` HEAD when a save
    opens a session) while L214 says "User can change branch in Settings page". The value is
    surfaced with a hint and `readOnly`, and never joins `edits`, so Save cannot send it — asserted
    by PUT-body equality in the settings spec. Rationale: a hand-edited branch would silently
    redirect every following commit off the pipeline's strategy, and there is no validation this
    UI could do that the save pipeline does better. **Flagged for the lead** as a spec deviation.
12. **The empty history state is the common case, not an edge case.** The first-startup import
    inserts `entry_status` rows and *no* `status_history` rows (D37), so every imported entry shows
    "No status changes recorded yet." until its first transition; the panel says so explicitly
    rather than rendering an empty box. The read is `retry: false` so the untracked 404 shows its
    message immediately instead of after three retries.
13. **The history panel is a page section, not a seventh tab.** `CardTitle` is a styled `<div>` in
    this repo, so the section attaches `role="heading" aria-level={2}` at its call site (no change
    to the shared primitive). The detail page still has exactly the six read-only tabs.
14. **`HistoryPanelState` is a pure function** (`loading → untracked → error → empty → ready`) so
    the five states are unit-tested without a browser; `newestFirst` reverses the endpoint's
    oldest-first rows rather than re-sorting by `changed_at`, which keeps the order stable for
    same-second rows (the endpoint orders by `status_history.id`, `server/src/services/status.ts`).

## corrections the specs forced (the tests changed the code, not the reverse)

* **The portal click trap (decision 3).** The first full tier-1 run navigated away from the table
  when an action was chosen — a genuine bug, now fixed and pinned.
* **The timeline's concatenated words (decision 10).** `toContainText('DS-ACAD1-C01-001 marked
  verified')` failed against `DS-ACAD1-C01-001marked verified`; the markup now renders the space the
  spec draws.
* **Two assertion techniques had to change because the measurements were wrong, not the app:**
  (a) dev-mode StrictMode double-mounts `GET /api/quests`, so "the list request count is still 1"
  is not a usable anchor — `tests/ui/quests-mocks.ts` now records **withheld responses**
  (`patchResponses`) and the spec proves the flip while the PATCH response has not been sent (a
  strictly stronger claim than counting refetches); (b) while a Radix dialog is open the page behind
  it is `aria-hidden`, so `page.getByRole('main')` resolves nothing — the rollback assertions read
  the badge with an attribute selector (`badgeBehindModal`) and the helper carries the why.
* No existing test was weakened. p2-08's placeholder assertions were **replaced by construction**
  (the placeholder button, its two tooltip/label constants and their assertions are gone), the
  detail header test gained the two actions, and the settings test gained the git_branch case.

## not claimed here (honest gaps)

* **Tier 2 is the lead's**: the AC's own browser/real-corpus pass, a real `status_history` row read
  back from the real database, and the real `content/YYYY-MM-DD` branch. Every number in this file
  is tier 1 (route-mocked, hermetic, no CLI/.NET/sibling repo/network).
* **The server was not exercised and not modified.** The PATCH and history contracts used here are
  the mocks' reading of `docs/spec-api.md` + D37/D51(f); the server's own behaviour is covered by
  p2-01/p2-02's unit tests and the lead's tier-2 pass. Nothing in `server/` was touched.
* **The `git_branch` hint's claim is documented, not measured**: "set automatically when a save
  creates this session's branch" is D42/spec-derived; this story proves the value renders read-only
  and cannot enter a PUT body, not that the save pipeline created that branch.
* **The menu is not a keyboard ARIA menu** (decision 2): Tab reaches the trigger and both actions;
  Up/Down roving focus is deliberately absent rather than half-claimed.
* **768px exactly is untested**, as in p2-06/p2-07/p2-08 (the specs drive 375 and 1280).
* **"Verified on a live Imlight server" semantics are not checked** — the lifecycle's third status
  is a bookkeeping transition here, as the specs define it.
