HOW IT BEHAVES
  * The check is lazy: zero `GET /api/quests` until the first save click; one read
    per results set (not one per click), refreshed after a save created quests.
  * Save All shows the AC sentence EXACTLY as before
    (`Save {N} quests to SpiralDB? This will create files and auto-commit.`) and
    renders the existing names next to it in the same dialog:
      heading: "These quests already exist in SpiralDB and will be overwritten:"
      then an <ul aria-label="Quests that will be overwritten"> of names, in
      extraction order, deduplicated. A quest that is NOT in SpiralDB is never
      listed.
  * Save Selected asks only for an existing name. Its wording is:
      title:       "Overwrite quest"
      description: "Quest {name} already exists in SpiralDB. Saving will overwrite
                    that file, refresh its metadata and auto-commit."
      buttons:     Cancel / Overwrite
    A new quest keeps today's one-click behaviour (no prompt).
  * While the check is in flight the Save button is disabled; the action-bar
    buttons are disabled too, so a second click cannot race it.

FAIL-SAFE DECISION (the list fetch fails ⇒ FAIL CLOSED, nothing is saved)
  A failed `GET /api/quests` cannot be degraded into an unconfirmed overwrite, and
  it cannot be "assumed empty", so the page refuses to save at all:
    Save Selected → no dialog, no POST, one error toast.
    Save All      → the dialog opens with the reason and the consequence, and its
                    Save button is DISABLED (only Cancel is available).
  The message is `existingCheckFailedMessage(existingCheckErrorMessage(error))`:
    "<server's own message> Nothing was saved: the check has to succeed before a
     save, so an existing quest is never overwritten without warning. Try again."
  The memo is cleared on failure, so the next click really retries rather than
  replaying the rejection.

HOW IT BEHAVES
  * `source` is sanitised: trimmed, reduced to its BASE NAME (split on `\` and `/`,
    keep the last component), control characters stripped, capped at 255 chars.
    `../../etc/passwd` → `passwd`; `/tmp/x/session_1.json` → `session_1.json`;
    `C:\Users\j\captures\session.json` → `session.json`; `""`/`"   "`/`null`/a
    non-string → no note at all (absent ⇒ exactly today's behaviour).
  * On a CREATE the single `status_history` row is
      old_status: null, new_status: 'extracted',
      notes: 'Imported from packet capture {base name}',
      changed_by: <settings.user_name>          (exact text, no suffix)
  * On an UPDATE: no history row is added and the status is never touched
    (D49(d) — no user-facing transition on an update).
  * The response shape is unchanged (`source` is not echoed).

HONEST NOTES / RISKS
--------------------------------------------------------------------------------
  1. NOTHING IS COMMITTED (the task says not to), and no real save was performed:
     the browser + real git path is the lead's tier-2 pass. The unit tests do
     exercise the real save pipeline (write + metadata + commit + status) against
     throwaway repos, so the note's DB row is pinned for real.
  2. Fail-closed means a transient `GET /api/quests` failure blocks saving until it
     succeeds. That is deliberate (the alternative — saving without knowing what
     would be overwritten — is exactly what gap A forbids), and it is recoverable
     by clicking again.
  3. `GET /api/quests` scans + JSON5-parses the corpus per request (D12, ~tens of
     ms for 322 files). The overwrite check therefore costs one extra list read per
     results set, not per save click.
  4. The plan's note text is written to `status_history.notes` only; the git
     commit body stays empty (the endpoint's `notes` field is the commit body and
     the client sends none) — that matches the p2-05 commit-format expectation.
  5. Pre-existing, unchanged: the 5 s "Extracting quests..." info toast overlaps
     the bottom-right action bar, so Playwright waits for it to auto-dismiss on the
     Save All / existing-name Save Selected clicks (≈6 s per such spec). This
     predates this round (docs/evidence/phase-2/story-p2-07-ui.txt shows the same 6.1 s), and I did
     not change the toast policy.
  6. What I think the plan got wrong / leaves open: plan §2.4 says extraction saves
     "set status='extracted' with history note ..." without saying what an
     extraction save of an ALREADY-EXISTING quest should do. I resolved it with
     D49(d) (no note, no status reset) per this task's instructions, but the plan
     text alone would read as "always write the note", which would also rewrite a
     `verified` quest's history on every re-extraction.
