## decisions the AC leaves open (and how each was settled)

1. **How the stateful list represents "grows by N".** `mockApi` gained `browseRows?: MockQuestRow[]`:
   the `GET /api/quests` answer is built with quests-mocks.ts's `questListBody(rows)` over a mutable
   array, and the default (200) `POST /api/quests` path pushes one row derived by `browseRowFor`
   **before** answering — the client invalidates `QUESTS_QUERY_KEY` on success, so the browse page's
   refetch must already find the new row. `browseRowFor` mirrors the server's own derivation
   (`server/src/services/sync/corpus.ts` -> `buildQuestRows`): title = `m_questTitle`'s raw key with
   `title_source: 'rawKey'` (an unsynced tier-1 DB holds no string-table entry, D49(g)) or the quest
   name with `'missing'`; level / goal_count / is_mainline from the saved object; status `extracted`
   (D49(d)). Only that default path grows the list — an `onSave` override owns its own answer, so a
   409/500 override can never add a row.
   M is `browseSeed()`: two real corpus names (`MB-YARD1-C01-001`, `WC-CYCLOPS-MAIN-002`) deliberately
   **disjoint** from the capture's quest (so the save is a create, not gap A's overwrite) and
   `reviewed`/`verified` (so the Extracted count genuinely starts at 0). Beyond name and status their
   columns are placeholders — the chain asserts the count, the statuses and the grown row, not those
   two rows' fields.
2. **N > 1 kept, as a second spec in the same describe.** `verify-captures.mjs` asserts **exactly one**
   reconstructed quest for every committed fixture (all five), so no capture in this repo can honestly
   produce two: the N = 2 chain takes N from the mocked endpoint and uploads the file's pre-existing
   inline stub (`session_2026-09-24.json`, 15 B), which is the one place N can come from in tier 1.
   The real-capture chain is therefore the N = 1 spec, and it is the one that maps 1:1 onto AC#13's
   "a D28-generated capture" clause.
3. **The real-capture extraction answer's values are the corpus's own, not invented.** A mocked
   endpoint is unavoidable (no CLI), so `REAL_CAPTURE_QUEST` stands in for the CLI's output; its
   title (`QuestTitle_1625CA`), level (0), mainline and 7 goal names/types were read from
   `data/test-spiraldb/QuestTemplates/questtemplates_WC-UNICORN-MAIN-004.json` at the README's pinned
   corpus commit `c55ccab175440c5f676b8d5315575ccd6d550332`, and `verify-captures.mjs` compares
   exactly those fields in order. The chain asserts name / level / goal count / `new` — the fields its
   browse row and save body are built from.
4. **`source` vs the capture note.** The browser only ever sends `source`; the note text
   `Imported from packet capture {source}` is composed server-side on the first `entry_status` insert
   (D50(i)) and is unit-tested there (`tests/unit/save-pipeline.test.ts`). Tier 1 therefore asserts
   the wire body's `source` and does not re-assert the server's sentence; the real note is the lead's
   tier-2 surface.
5. **Assertion strength.** "grows by N" is asserted four ways (rendered row count, pagination label,
   both tab count badges, and the identity of the grown row) plus the refetch itself, rather than by
   one proxy number.

## not claimed here (honest gaps)

- **The CLI is not exercised.** Both new specs mock `POST /api/extract/quests`; the claim that this
  capture parses to exactly one quest rests on `scripts/verify-captures.mjs` and the README's pinned
  sha256, and **neither runs in CI** (it needs the .NET CLI and the disposable corpus clone). The
  lead's tier-2 pass is the only place the real binary can confirm it.
- **No CI run was observed by me** — only the local `npm run test:ui` (the same command the `ci` job
  runs). The headless-vs-headed question is settled by `playwright.config.ts` (`headless: true`) and
  by the local run, not by a runner log.
- **The pinned numbers break loudly on a corpus refresh**: `REAL_CAPTURE.byteLength === 14235` and the
  card's `13.9 KB` are tied to the committed fixture (the README pins the same file by sha256). A
  regenerated fixture fails this spec until both numbers are updated deliberately — intended, but it
  is a maintenance coupling worth stating.
- The N = 2 spec's quest objects are the file's pre-existing inline fixtures (QUEST_A / QUEST_B), not
  corpus-measured; nothing in that spec claims they are.
- **The AC's "N quests" clause is structurally N = 1 for every committed artifact**: `fixturegen`
  takes exactly one `--quest` per invocation, so a capture yielding more than one quest cannot be
  committed with the current generator, and `verify-captures.mjs` asserts exactly one for all five
  files that are. The general-N path is therefore covered only against the mocked endpoint (spec 22);
  a real multi-quest capture through the real CLI stays unverified until tier 2 has a capture that
  yields one.
- **The stateful mock's row derivation is a mirror, not a re-derivation.** `browseRowFor` copies the
  rules I read in `server/src/services/sync/corpus.ts` -> `buildQuestRows` (rawKey/missing title,
  level, goal count, mainline, `extracted`) and the D49 row contract; tier 1 cannot detect a real
  server whose row derivation differs, because the list response is the mock's. The real post-save
  rescan is visible only in the lead's tier-2 pass.
- Prettier's `npm run format` rewrote no file other than tests/ui/extraction.spec.ts (it was already
  conformant; the run reported "unchanged" for every other file), and `git status` shows exactly one
  modified path plus this untracked evidence file.
