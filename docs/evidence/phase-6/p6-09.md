## ac1 — the scaffold validates against the corpus schema (the live boot is p6-12's)

**The split, as agreed with the lead before any harness work.** The live Imlight boot and the
"quest-template count rises by exactly one" assertion are **task 6.11 / story p6-12's** — its own
criterion already requires exactly that assertion, from Imlight's own
`SpiralDB loaded … quest templates` log line. Building the 866 MB copy, the Aurorium launcher and the
.NET 10 boot here would duplicate that story. This story owns the **scaffold and its schema
validity**; p6-12 owns the **boot and the count**.

**Validated, not eyeballed, and by which validator.** Every scaffold arm goes through
`SaveQuestRequestSchema` — the schema `POST /api/quests` itself validates with (which embeds
`QuestTemplateSchema`, task 3.1's 36-field corpus schema) — and the bytes are read back through the
pipeline's own lenient reader. The corpus's canonical *shape* was re-derived independently by the
census: `docs/evidence/phase-6/p6-09-census.txt`, whose two distinct orders are **320 files × 36 keys**
and **2 files × 18 keys** (`WC-CYCLOPS-MAIN-002`, `WC-UNICORN-MAIN-004` — the extractor's own sparse
output, which ac2's "all 36 keys … with explicit nulls" is written *against*, not a scaffold target).

**The reproducible command for p6-12** (a named scratch DB + the clone; it names both paths it
resolved before writing, and it refuses to pick a database implicitly):

```
NODE_ENV=test SPIRALDB_UI_DB=$PWD/data/__test-scratch__/p6-12.db \
  npm run scaffold:quest -- --name <QUEST_NAME>            # writes into settings.spiraldb_path
# or explicitly:
npm run scaffold:quest -- --name <QUEST_NAME> --db <file> --spiraldb $PWD/data/test-spiraldb
```

**Loadability, measured rather than assumed** (`docs/evidence/phase-6/p6-09-loadprobe.txt`): a
throwaway .NET project (`data/__test-scratch__/p6-09-loadprobe`, gitignored — CI has no .NET at all,
D55) deserializes candidate documents with **Imlight's own settings**
(`TypeNameHandling.Auto`, `NullValueHandling.Ignore`, `SpiralDB.cs` L48-51) against the **real
generated `Imcodec.ObjectProperty.TypeCache.QuestTemplate`**:

```
candidate A (p6-09's skeleton: corpus scalars, nulls where the corpus has nulls): LOADED
candidate B (D101 read literally: null in every non-name/non-title/non-container key): LOADED
=== 2. does m_dialogList need its $type?
  with $type   : LOADED, resolved type = ActorDialogList,       m_dialogs.Count = 1
  without $type: LOADED, resolved type = ActorDialogListBase,   m_dialogs.Count = <no m_dialogs property>
=== 3. one JSON null per member type, against the real QuestTemplate
  m_questNameID (uint)   null -> LOADED, value = 0
  m_prepAlways (bool)    null -> LOADED, value = False
  m_activityType (enum)  null -> LOADED, value = ACTIVITY_NotActivity
=== 5. the control: the corpus's own minimal file (WC-TUT-C03-002)
  WC-TUT-C03-002 (verbatim): LOADED
```

Two findings from it, both recorded because they decide shape:

1. **`NullValueHandling.Ignore` skips nulls on deserialization**, so a `null` in a value-typed member
   is *not* rejected — the CLR default is kept. (My recollection said Json.NET throws; it does not, and
   the criterion's literal reading is therefore loadable.) The skeleton still writes the corpus's own
   scalar (`0`, `false`, `"ACTIVITY_NotActivity"`) because **322 of 322 corpus files carry those**, and
   a null there would be a scaffold-only byte shape — the same class as a top-level `$type`. The plan's
   "all 36 keys … with explicit nulls" is read as *"all 36 keys present, with an explicit `null`
   wherever the corpus has one"*, and that reading is reported rather than silently adopted.
2. **The nested `m_dialogList.$type` is load-bearing.** Without it Json.NET binds the wrapper to
   `ActorDialogListBase`, **which has no `m_dialogs` member** — a non-empty list loads with its dialogs
   silently dropped. All 320 canonical files annotate it, so the scaffold does. The *top-level* document
   has no `$type` (322/322 corpus files carry none), so the two rules are kept apart deliberately.

**The nulls, key by key.** The scaffolded `LM-NIGHT-MAIN-009` differs from the corpus's own minimal file
in **exactly three lines** (`docs/evidence/phase-6/p6-09-minimal-diff.txt`): the name, `m_questTitle`
(`null` vs the corpus's `""`), and `m_isHidden` (`false` vs the corpus's `true` for that hidden tutorial).
Everything else — all 13 explicit nulls, the empty containers, the scalars — is the corpus's own
minimal-file shape. The 13 explicit nulls are `m_questInfo`, `m_questPrep`, `m_questUnderway`,
`m_questComplete`, `m_requirements`, `m_prepRequirements`, `m_pruneRequirements`, `m_clientTags`,
`m_missionDoors`, `m_dynaMods`, `m_defaultDialogAnimation`, `m_questEffectInfoList`, `m_behaviors`.

**`m_questNameID: 0` — the id side, stated because the criterion names it.** The corpus is unanimous:
**322 of 322** files carry `0`, never the quest's numeric id — the id lives in the `m_questTitle` key
(`QuestTitle_1ED8D` → 0x1ED8D), which is how Imlight's loader reaches the quest's text. The catalog
*does* know the linked id (`quest_ids.quest_id`); writing it here would produce the only file in the
corpus with a non-zero value. **Nothing inferred is written anywhere in this document.**

|---|---|---|---|
| `DM-GRAVE-MAIN-008` (19 refs) | `direct` | `"QuestTitle_00002165"` | `Scaffolded from the quest catalog (link_kind: direct; title QuestTitle_00002165).` |
| `LM-NIGHT-MAIN-009` | `inferred` (basis recorded) | `null` | `Scaffolded from the quest catalog (link_kind: inferred; no title: only a direct link writes one, and this link is inferred).` |

`LM-NIGHT-MAIN-009`'s database row **does** hold `title_key = QuestTitle_173223` (the id tier's own

"QuestTitle_00002165"` vs `"m_questTitle": null`; the key is present in both files (D57: the writer

**How the direct key is resolved, and where it cannot be.** The catalog persists the direct link's key

write **no title**: picking one of two ids that share a string is a guess about identity, not a
recovery. *(A `quests.title_key` column would make this exact and remove the reverse lookup; the sync
today keeps the key only in `quest_ids`, which exists only for ids with text rows. Reported, not
widened into p6-04's committed module.)*

## D17 / restore, and the branch trap this run hit

**Restore, five axes + the corpus count + the ref list** — after the two scaffolds and the two syncs:

```
BEFORE the reset:  branch content/2026-09-27 · HEAD c061f734 · main f3f8b5c0 · count 44 · porcelain []
AFTER  the reset:  branch content/2026-09-27 · HEAD 18dc9247 · main f3f8b5c0 · count 42 · porcelain []
                   QuestTemplates/*.json = 322
                   refs: 18dc9247 content/2026-09-26 · 18dc9247 content/2026-09-27 · f3f8b5c0 main
```

**A real trap, hit once, and the decision it produced.** The first CLI scaffold run used a scratch
database whose `settings.git_branch` was `content/2026-09-28` (today) while the clone sat on
`content/2026-09-27`. `ensureSessionBranch` found that branch absent and **created it from `main`**,
checking out main's tree — which silently dropped the clone's two branch-only files
(`WC-CYCLOPS-MAIN-002`, `WC-UNICORN-MAIN-004`) and left a stray branch: the **D76(b) shape**, one level
deeper (there a `reset --hard` stranded a branch; here the **database's branch name disagrees with the
tree**). It was cleaned up completely (`git checkout` the original branch, `git branch -D` the stray
one), and the run above is the corrected one. The story's test never hit it because it sets that
setting explicitly and its five axes include the ref list.

**The decision, in one pure function** (`resolveScaffoldBranch` in `services/questScaffold.ts`, which
the CLI calls — so it is unit-tested rather than being CLI prose):

| case | behaviour | why |
|---|---|---|
| no `--branch` (the default) | **follow the checked-out branch**: the setting is moved to it (`writeSetting`), and the CLI prints `git_branch updated <branch> (was "<old>"; the working tree is on it, and committing to another branch would create it from main and strand this one)` | the caller pointed the command at a *repository*; the only branch that cannot strand work is the one already checked out. It is also the cheapest correct default — the operator does nothing |
| `--branch <name>` **equal** to the checked-out branch | proceed (setting moved if it disagreed) | explicit and safe |
| `--branch <name>` **not** checked out | **refuse, exit 1**, with the two remedies: `git -C <root> checkout <name>`, or drop `--branch` | creating it from `main` *is* the stranding behaviour, and the fix belongs in git where it can be reviewed — not in a database setting |
| no repository context (not a git working tree) | pass the setting through unchanged | nothing to follow; the pipeline's own default applies |

Exact refusal text (verified against the clone, which was on `content/2026-09-27`):

```
[spiraldb-ui] Refusing to scaffold on branch "main": the working tree is on "content/2026-09-27".
Committing to a branch that is not checked out creates it from main and replaces the tree with main's
contents, stranding anything that exists only on "content/2026-09-27". Check it out first
(git -C <root> checkout main) or drop --branch to commit on "content/2026-09-27".
```

And the default, demonstrated against a **throwaway repository** (never the clone —
`data/__test-scratch__/p6-09-branchrepo`, whose scratch DB was seeded `content/2099-01-01`):

```
[spiraldb-ui] git_branch setting   content/2099-01-01
[spiraldb-ui] working tree branch  main
[spiraldb-ui] git_branch updated   main (was "content/2099-01-01"; the working tree is on it, and
                                    committing to another branch would create it from main and strand this one)
```

The **alternative I rejected**, for the lead's decision: refusing whenever the two disagree. It is
safe, but it makes the common case (a freshly seeded scratch DB + a clone on a content branch) need a
manual `UPDATE` before every run, and a command that must be corrected by hand each time is a command
whose guard gets bypassed by habit. The third option — checking a branch out from inside the tool —
mutates git state the operator owns, which a scaffold command has no business doing.
