## ac2 — the hold-out protocol, recovered and independently reproduced

The plan and the findings doc name a hold-out figure but never its protocol. The executor recovered it and the lead re-implemented it from the executor's prose, in code the executor did not write:

> *group* = the name's prefix before its last `-<digits>` suffix; *held out* = every element with a preceding **and** a following sibling, ordered by name (n−2 per group); *interpolate* = midpoint `floor((before + after) / 2)`; *hit* = exact id equality. The accept rule is **not** applied to it.

```
$ python3 /tmp/p6/p6-04-holdout-probe.py
owner fork (321): pairs 321 | groups(>=2) 59 | ascending 51 | contiguous 38 | cases 168 | 131 hit / 37 miss = 78.0%
D17 clone  (315): pairs 315 | groups(>=2) 59 | ascending 51 | contiguous 38 | cases 168 | 131 hit / 37 miss = 78.0%
```

Two independent implementations reproduce the findings doc's **59 groups / 51 ascending / 38 contiguous fingerprint exactly** and its **37 misses exactly**, on both corpora — which is what identifies this as the doc's own protocol. The headline **78.0%** stands. **The doc's `128 hit / 165 cases` does not reproduce**: the protocol yields 131 hit / 37 miss of **168**, and no restriction tried (including requiring both anchors to have a non-empty `WizQst` table, which gives 165 cases but 34 misses) produces 128/37 together. The 3-case residual is recorded, not tuned. The findings doc and D106 are annotated with this in the same commit.

## Findings that extend the findings doc (all measured)

1. **`m_displayName` is not always a key.** Of the 423 direct-pair rows, 313 are `QuestTitle_*` (→ 286 names) and **110 are literal titles** ("To Tame a Tempest" ×20), which the doc's prose implies cannot happen.
2. **A second name→id path exists**: 83 of those literal names resolve through a `QuestTitle_*` **value** lookup in `string_table`. It does not change 286 (the criterion is the key-shaped pair) and its hold-out fingerprint is not the doc's.
3. **Reference rows do not map 1:1 to `quest_catalog_refs`**: 3,003 rows → **2,796** distinct `(quest_name, wad, entry, class, goal_name)` tuples, so **207 rows collapse** under the spec's `UNIQUE`. **p6-05's insert must be idempotent and `reference_count` must not be the raw row count.**

> **Correction (added by p6-05, measured): the UNIQUE absorbs 148 rows, not 207.** p6-05's real sync keeps
> **2,855** rows of the 3,003 raw (148 not inserted), not 2,796: SQLite's `UNIQUE` treats a **NULL `goal_name`
> as distinct**, and 979 rows carry one, so 59 rows survive that a NULL-agnostic count would collapse. The
> **207** above is the difference between the raw count and the NULL-agnostic key space — a true statement
> about the key space, and **not** a statement about the insert. Both readings are now printed on their own
> labelled lines by the sync, and `reference_count` sums to 2,855 = the table's own row count.
4. **`m_questName` can be absent, not just empty** (525 nodes have no key at all), so ac3's "empty `m_questName`" covers only one of the two shapes; the report counts both and names them separately.
5. **The `QuestTitle_*` spelling is not derivable** from the id (both `QuestTitle_1ED8D` and `QuestTitle_00002173` exist; the zero-padded/stripped alternatives do not), which is why the injected interface is an id→key resolver rather than a spelling rule.
