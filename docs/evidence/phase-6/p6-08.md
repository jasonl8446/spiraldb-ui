# p6-08 — evidence panel + one-click insert (task 6.7)

**Story:** p6-08 · **Branch:** phase-6-quest-catalog · **Implemented by:** a fresh `omd-agent-executor` · **Verified by:** the lead, with an instrument the executor did not write (the reducer applied to a real corpus document in memory, path-by-path).

## What shipped

**The insert reducer** (`client/src/lib/evidence-insert.ts`, pure — imports `@shared/document` only): `planEvidenceInsert(row, target, doc?) → DocEdit | refusal`. Target resolution is three rungs — a **used text row** writes its own provenance path when that path is one of the three fields the plan names, otherwise the **focused** field, otherwise **no edit plus a sentence**. Dialogue rows follow only the focused entry. Refusals are `no-key`, `no-target`, `incompatible`, each with its own message.

**The panel** (`client/src/components/quest/EvidencePanel.tsx` + `EvidenceFocus.tsx`) in the one right rail (`Evidence │ JSON`, `?panel=evidence`), beside the editor in **both modes**; inserts exist only in edit mode because they come from the editors' focus channel. `shared/document.ts` gained `parseDocPath` (the inverse of `formatDocPath`) rather than a second path grammar.

### The lead's independent half — the reducer applied in memory, path by path

Applies the reducer's plan to the **real** corpus file with `setAtPath` and diffs every leaf path of the serialization. It uses **real wire rows** from the lead's own live capture of the p6-07 endpoint:

```
DIALOGUE insert "WizQst17318F_00000000" at m_goals[0].m_dialogList.m_dialogs[0].m_dialogEntries[0].m_dialog
  plan.value = "WizQst17318F_00000000"  source = focus
  CHANGED LEAVES: ["m_goals[0].m_dialogList.m_dialogs[0].m_dialogEntries[0].m_dialog"]
TEXT insert "WizQst17318F_00000000" -> CHANGED LEAVES: ["m_goals[2].m_goalText"]
  2 passed (2)
REFUSAL KINDS (dialogue->goal-text field, empty key, no target): all three refused
```

**Exactly one leaf changes in both arms, and the value written is the string-table KEY, never the resolved text** — which is the fact that decides correctness, because every downstream reader resolves those fields through `string_table`. The second arm also proves the **field is added**: `m_goalText` is absent from the document. The probe was a throwaway vitest file, run and deleted (never committed).

### Three of the lead's own probe errors, recorded because they were all the lead's

(i) it ignored `setAtPath`'s **return value** (the primitive returns the document) so every diff came back empty; (ii) it **guessed the row-source shapes** (`{key, field}` and `{index, field, dialog_key}`) and passed extra properties; (iii) it passed a **dialogue row's `field` as the insert target** — and that field names the dialog **entry** (`…m_dialogEntries[0]`), not the `m_dialog` leaf, so the reducer correctly refused `no-target`. The reducer was right in all three cases. That last one is a real documentation gap the lead closed in `spec-api.md`: `dialogue[].field` is the entry path, `text_rows[].field` is the value's own path.

## Decisions this story forced (all recorded outside the code)

- **D117** (`plan-overview.md`): the unit suite now runs **one file at a time**, because the D17 clone has **two** writers and the race D66(g) predicted stopped being latent — a parallel run failed **both** clone suites. Cost ~11 s → ~51 s, stated so a future reader does not "fix" the parallelism back on. Two alternatives (a cooperative lock; a throwaway clone per suite) are recorded as considered-and-not-taken with the reversal path.

- **The plan's "goal text" arm annotated**: `m_goalText` is absent from **0 of 772** corpus goals and **no `WizQst*_Goal*Text` row exists in `string_table` (0 of 216,991)**, so that arm *creates* the field (schema-valid, proved against the save schema) and the insertable rows are ordinary rows of the quest's own table.

- **The lead's spec fix**: `dialogue[].field` points at the dialog **entry**, not the `m_dialog` leaf — a consumer deriving an insert target must append `.m_dialog` (or use the focus).
