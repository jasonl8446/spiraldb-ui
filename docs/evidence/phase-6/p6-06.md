# p6-06 — names everywhere: the pair, search-either, and the NPC namespace (task 6.5)

**Story:** p6-06 (D105 / P6-16 + P6-17's namespace) · **Branch:** phase-6-quest-catalog · **Implemented by:** a fresh `omd-agent-executor` · **Verified by:** the lead, whose own probes were written before reading the module.

## What shipped

**One display rule** (`client/src/lib/display.ts`): `namePair` is the single construction of `Name (ID)`; `npcDisplayName` delegates to it, `friendlyNameOf` is the single accessor for the friendly half, and `formatNameRow` pairs **quests** (`title (quest_name)`, gated on a *resolved* title), **zones** (`display_name (zone_path)`) and **npcs**. Items/spells/drop_tables/strings stay unpaired.

**The server emits data, never formatting**: `ObjectListRow.friendly_name` is resolved from the same `NAMES_TYPE_SPECS` row the names API serves, with `friendlyNamesType`/`friendlyNameNote` on `shared/objectTypes.ts` so the search joins, the list rows and the detail headers cannot disagree.

**Search either**: `?q=` matches the id column for the six two-column types; `SEARCH_GROUPS` derives its `nameJoin` from that same field; `drop_table`/`creature_spellbook` deliberately gain no arm.

**The NPC namespace** (`server/src/services/npcNames.ts`): keyed on the NPC with its strings as aliases.

## Carried, and owned (the spec says so)

`GET /api/npcs/:id` **did not ship**, and the reason is a real dependency rather than an omission: its `dialogs`/`quests` arms need the **speaker ladder** that task 6.6's evidence API builds, and empty arrays would claim "this NPC has no dialogs". `docs/spec-api.md` now carries a scope note naming that dependency and the new owner, so the endpoint is **not described as shipped** and its counts claim is recorded as *untested rather than satisfied*. The alias namespace, the `npc` search group and the one-row-two-aliases result did ship.
