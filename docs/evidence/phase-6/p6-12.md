# p6-12 — the live-load harness: Aurorium serves, Imlight loads (task 6.11 / P6-18, P6-19)

**Story:** p6-12 · **Branch:** `phase-6-quest-catalog` · **HEAD when run:** `74c18dc` ·
**Implemented by:** a fresh `omd-agent-executor` · **Verified by:** the lead.

Task 6.11 is the story the loadability bar (D113) needed and the plan did not have. It ships a
harness whose *decision* logic is a pure module and whose side effects are one CLI: the module is
what `npm test` exercises (through an injected fake log), the CLI is what boots the real chain.

## What shipped

| Path | What it is |
|---|---|
| `server/src/services/imlightHarness.ts` | Every decision, pure: port ownership, Aurorium's identity probe, the `SpiralDB loaded` parser, the +1 proof, the freshness computation, the clone snapshot/restore plan and the axis comparison. **No** node imports — that is asserted, not promised. |
| `scripts/imlight-boot.ts` | Every side effect: TCP probes, `ss` + `/proc` attribution, the Aurorium launcher and its config/DB copy, the prebuilt-output copy, the config pins, the Director boot/watch/stop, the scaffold subprocess, the clone restore, the evidence files. |

| `docs/evidence/phase-6/p6-12-*.txt` | The raw logs and the raw outputs this document quotes. |

`3` a port answers from a process this harness cannot use · `4` stale prebuilt · `5` no log line ·

**A restart, deliberately, and said out loud.** SpiralDB is loaded once per boot, so the after-count
can only come from a second boot — "the same process shape", meaning the same run directory, the
same config copy, the same `DOTNET_ROOT`, and the same corpus. Four guards make the comparison
mean something, and the third is the one that would have caught a dishonest proof:

1. the two lines are the **process under test's own** stdout (`SpiralDB.Load@L149`), never a fixture;
2. **all seven non-quest families are asserted equal** between the two boots — two corpora would
   otherwise produce a "+1 quests" reading that says nothing about the scaffold;
3. **both of the line's file counters move by the same delta** (`files` 2274 → 2275 *and* quest
   templates 322 → 323). A pair where only one moved is a different process shape, not a scaffold;
4. the delta is exactly the expected one.

The line appears **three times inside one process** (measured: patch, login and game each touch the
collection), all three identical; the harness asserts they agree inside a boot rather than picking a
favourite — three agreeing readings of one process are a stronger baseline than one.

**Reuse arm.** A second run, with the first run's Aurorium deliberately left alive

The ledger is `tools/.aurorium-run/ownership.json` and it stores pid **+ start time + command line**,

**Two gates, not one.** Process identity is anchored to a path, so `node -e "// aurorium decoy"` is
not accepted (`serviceOfCommandLine` is unit-tested against that string), and for 12369 a second,
independent gate asks **Aurorium itself**: `GET /latest` must return the revision the workspace index
holds. A decoy that pretends to be Aurorium's binary cannot pass the first gate; one that only
*answers* cannot pass the second.

**The five ports, attributed live.** A sampler read `ss` every second through a boot
(`p6-12-ports-live.txt`):

```
LISTEN 0 128  127.0.0.1:12369 … users:(("aurorium",pid=1807174,fd=13))
LISTEN 0 4096 0.0.0.0:12500   … users:(("dotnet",pid=1807204,fd=149))
LISTEN 0 4096 0.0.0.0:12000   … users:(("dotnet",pid=1807204,fd=174))
LISTEN 0 4096 0.0.0.0:12333   … users:(("dotnet",pid=1807204,fd=187))
```

`8080` is **not** in that sample and the reason is boot order, not a gap in the check: the Director
reaches `PlayerDatabase.Instance.Store` — which binds 8080 — *after* it logs `SpiralDB loaded`, and
the harness stops it as soon as the line appears. Attribution by ancestry is demonstrated live
elsewhere: a harness run whose process was killed by a broken pipe left the Director running, and the
next `probe` reported

```
8080  imlight  owned  1801139  port 8080 answers from pid 1801139 (dotnet --fx-version 10.0.12
      /…/tools/.imlight-run/RavenDBServer/Raven.Server…), recorded as the imlight this harness started…
```

— the socket's owner is the RavenDB **child**, and the ledger holds its parent, so the match is by
ancestry. `classifyPort` walks `/proc/<pid>/stat`'s ppid chain for exactly this reason.

**Two refusals, not one, and the second is a reading rather than the letter.** A live *Aurorium* on
12369 is reused (its HTTP port is shareable and D114 says an already-answering service is left
alone). A live *Imlight* on any of its four ports is refused **naming the port**, because this
harness reads the log of a Director *it started* — it holds no other process's stdout, so an
Imlight it did not start cannot serve the assertion. Both directions are the same rule
("ownership follows the starter"); only the refused half has no reusable alternative.

- both sides are normalised through `shortBranchName()`, and the test now passes full refnames to a

- a failing restore step no longer aborts the restore: failures are collected, printed, and the axis

## Contradictions and corrections, stated rather than adjusted

1. **Task 6.11's blocker 2 is half right** (`p6-12-blocker-2-measurement.txt`). `LocalWadCachePath =
   ./cache` **is** cwd-relative (it is a LiteDB *file* and it grows to 284 MB after caching Root.wad),
   and so is `Logging.LogPath = ./logs/log.txt`. But `EmbeddedDatabaseDataDirectory =
   ../ImlightEmbeddedDatabase/` is **not** resolved against the Director's cwd: `tools/ImlightEmbeddedDatabase/`
   does not exist, and the database is written to `<run>/ImlightEmbeddedDatabase/` — the `../` is
   relative to Raven.Embedded's **RavenDB child**, whose own command line carries
   `--DataDir=../ImlightEmbeddedDatabase/` with `--Embedded.ParentProcessId=<director pid>`. The
   criterion's guarantee still holds (nothing leaves the workspace, and nothing is written into the
   Imlight tree), but the stated mechanism for that one path is wrong. Consequence for `.gitignore`:
   `tools/.imlight-run/` is the entry that matters; `ImlightEmbeddedDatabase/` had no directory to
   match here.
2. **Aurorium's `aurorium.db-shm` mtime moved.** The first version of the index copy opened the
   sibling's live database with SQLite read-only (`VACUUM INTO` from the source path), which bumped
   the mtime of `Aurorium/aurorium.db-shm` — a write into a repository this run must not write into,
   however transient the file. `aurorium.db` and `aurorium.db-wal` were never modified (their mtimes
   are still 2026-09-24 10:19). Fixed: the three files are now `cp`-ed into a staging directory and
   SQLite only ever opens the copy. Re-measured after the fix: `aurorium.db-shm` is unchanged across
   a full boot (`p6-12-aurorium-tree-untouched.txt`).
3. **`Aurorium/config.toml.bak` is untracked in that repo and is not mine** — mtime 2026-09-24 13:34,
   four days before this session.
4. **The dispatcher's probe is confirmed in every particular** I re-measured: the five ports were
   free at the start and are free now; the .NET 10 store SDK path is the one given; the prebuilt
   output is 866 MB with `Imlight.Director.dll` at `2026-09-27T10:32` local; the two commits after it
   touch only `docs/`; and the Aurorium binary and revision tree are where the probe said.
