**Why the column adds are a guarded step, and not four more lines of SQL.** SQLite has no
`ALTER TABLE ... ADD COLUMN IF NOT EXISTS`, and `initSchema` `db.exec`s every migration file on
**every** `openDb()` — the same database is opened twice in the output above, and on the second open
a raw `ADD COLUMN` would throw `duplicate column name: has_definition`. Of the three remedies the
brief allows, I took the **PRAGMA-guarded step**: it decides from `PRAGMA table_info(quests)`, so a
genuine duplicate-column error anywhere else still throws loudly, and it is directly testable
(`applyQuestCatalogColumnAdds` returns *how many* ALTERs it issued — 0 on the second call, measured
above and pinned in `tests/unit/db.test.ts`). Teaching the runner to tolerate that specific error
would swallow a real mistake; keeping the ALTERs as text cannot be made idempotent.

The empty tables are deliberate and structural: `quests` is one of the transactionally replaced
tables, and `quest_catalog_refs.quest_name REFERENCES quests(quest_name)` has no `ON DELETE` clause
while `openDb` turns `foreign_keys` on — so refs outliving their quest would fail the whole
transaction. The deletes are ordered **refs → ids → quests**, both catalog tables are in
`REPLACED_TABLES`, and a skipped stage never leaves a claim behind.

## The id-ownership defect the lead found, and the fix

The first build's `quests.link_kind = 'inferred'` was **6** while `quest_ids` held **5** inferred
rows; `LM-HEAP-MAIN-009` claimed an inferred link with no id row. `quest_ids.quest_id` is the
primary key, so **one name per id** is a structural fact: two names had interpolated the same
candidate id and the id-keyed writer kept one silently.

`resolveIdOwnership(records)` now decides ownership **before anything is written**: claims are
ordered **direct first** (a measured `<name>_Complete` + `QuestTitle_*` pair beats a 78%-accurate
interpolation), then by name; the first claimer owns the id; every later claimer is a **loser**
counted in both units, named in the report, and given `link_kind`/`title_source` = `none`. An
inferred loser also falls back to `quest_name` as its title, because an inferred title beside
`link_kind = 'none'` would be inferred material without its label.

### The two units, stated (D73(e))

`id_collision_names` counts **losing names**; `id_collision_ids` counts **distinct ids with more
than one claimant**. On this corpus they are both 2 (two names on each of two ids), but they differ
whenever one id is claimed by three or more names, so neither is ever printed without its unit.
Measured on this corpus — **the complete losing-name list, both entries** (the display sample is
capped at 5, so nothing is elided here):

| Losing name | Its established kind | Id it lost | Owner |
|---|---|---|---|
| `NV-PostWL-MAIN-002` | **direct** | 1608203 | `LM-PostWL-MAIN-001` (direct) |
| `LM-HEAP-MAIN-009` | **inferred** | 1524782 | `LM-HEAP-MAIN-007` (inferred) |

The sample text now attaches the kind to the **loser** — `NV-PostWL-MAIN-002 (direct) lost id
1608203 to LM-PostWL-MAIN-001` — because the earlier format put it after the owner's name, where it
read as the owner's kind and made the lead's arithmetic look like it did not reconcile.

### 286 → 285 and 6 → 5, in one place

### Determinism

The winner cannot flip between two runs of the same input: the order is a **total** order —
`quest_name` is unique across catalog records (the extractor's names come from a `Set`) — compared
byte-wise with `<` (never a locale collator), and `Array.prototype.sort` is stable (ES2019). The
unit test `resolveIdOwnership is deterministic and prefers direct evidence` feeds the same records
in a different order and asserts the identical owner, losers and samples.

## `reference_count`, and the three numbers around it

`reference_count` = the quest's **post-UNIQUE row count in `quest_catalog_refs`**, recomputed inside
the transaction after the refs are written (`UPDATE quests SET reference_count = (SELECT count(*)
FROM quest_catalog_refs WHERE quest_name = quests.quest_name)`). `sum(reference_count)` = **2,855**
= `count(*)` on the table: the table's own count, **not** the extractor's raw 3,003 rows (p6-04's
warning). The three readings that must never be substituted for one another:

| Reading | Value | Where it comes from |
|---|---|---|
| rows kept in `quest_catalog_refs` | **2,855** | the real `UNIQUE`; what `reference_count` sums to |
| distinct `(quest, wad, entry, class, goal)` with NULL `goal_name` read as `''` | **2,796** | p6-04's `reference_keys` — reported as `distinct_reference_keys` |
| distinct `(quest, wad, entry)` | **2,044** | the spec's narrower column comment |

2,855 > 2,796 because **SQLite's `UNIQUE` treats a NULL `goal_name` as distinct**: 979 kept rows
have `goal_name IS NULL` and never collapse (1,876 + 979 = 2,855), so 59 keys of p6-04's space
survive as separate rows. p6-04's 207 (`3,003 − 2,796`) is therefore *not* what the insert absorbed;
the real absorption is **148** (`3,003 − 2,855`). The CLI prints both, each on its own labelled
line, and a unit test pins the NULL behaviour (two NULL-`goal_name` rows to the same
`(quest, wad, entry, class)` → both kept, `reference_count` 2, `distinct_reference_keys` 1).

The id tier is the fourth number: `quest_ids` holds every numeric id with **at least one
`WizQst<id>_*` row** (4,823 = `coverage.id_space`) — "the id space the client holds text for"
(D97/D98's ~4,830). The 1,782 ids carrying only a `QuestTitle_*` key are deliberately *not* in the
tier (no text); `coverage.id_space` is `count(*)` on the table, so the number the UI reads cannot
drift from it.

## Contradictions with the spec, the plan or p6-04 (stated, not adjusted)

1. **The spec's `coverage` DDL did not parse.** `...(SELECT count(*) FROM quest_catalog_refs) AS
   references` → `near "references": syntax error` (reproduced independently by the lead, who fixed
   the spec). `references` is a SQLite keyword; the view is created with `AS "references"`, which
   keeps every column name byte-identical to the spec's contract.
2. **`quest_catalog_refs.class` cannot hold what its comment shows.** The spec annotates it
   `-- the referencing object's class (e.g. 'ReqHasQuest', 'ReqHasEntry')`, but p6-04 measured that
   **0 of 5,282** quest-bearing nodes carry `$type`: the requirement class is *inferred from the key
   set*. The column holds the NDJSON row's class (`WizZoneData`/`WizZoneTriggers`) — the value the
   tuple space is computed on and the one ac1's "0 rows without provenance" is about. The
   requirement class is not persisted anywhere (no spec'd column exists for it).
3. **`reference_count`'s comment is the third reading.** The spec says "referencing {wad, entry}
   pairs" (**2,044** here); the brief says "distinct referencing objects". The column is the
   post-UNIQUE row count (**2,855**) — the only value recomputed from what was merged and the only
   one that keeps `sum(reference_count) = count(*)`. All three are reported side by side; the lead
   is pinning 2,855.
4. **p6-04's "207 rows collapse" is not what the insert absorbs** — the real absorption is **148**;
   the extra 59 are NULL-`goal_name` rows SQLite keeps distinct. p6-04's number is a correct
   *key-space* count with NULL read as `''`, and its recommendation ("`reference_count` must not be
   the raw row count") is satisfied by 2,855.
5. **p6-04 counted one direction only.** Its `link_conflicts` (0 here — one name with two candidate
   ids) does not look at **two names for one id**, which is where the 2 real conflicts are. Both
   directions are now counted, in both units, with the losers named.
6. **p6-04's doc-comment says "the four non-numeric `WizQst` tables"; the live table has 7**
   (`WizQstBGH`, `WizQstDeath`, `WizQstExp`, `WizQstFire`, `WizQstIce`, `WizQstLife`, `WizQstStorm`).
   Measured with the same numeric-id rule (4,823 numeric ids of the 4,830 tables), so the exclusion
   behaviour is unaffected — only the count in the prose.
7. **The plan file's task 6.4 lists `quest_ids(...)` without `inference_basis`.** The spec (the
   contract the brief names) has it, and it is stored: every inferred row carries a non-empty basis,
   and no non-inferred row carries one.
