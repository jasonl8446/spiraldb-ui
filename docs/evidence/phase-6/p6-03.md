### Selection semantics implemented (and measured)

`--select` is a comma-separated glob list matched **case-sensitively against the full stored entry name**,
anchored at both ends — the same rule as `matchGlob`/`selectEntries` in `wadindex.ts`: `*` and `?` stop at
`/`, `**` crosses it, and every other character is literal. Measurement on both sides of that rule:

```
tools/bin/wad-scan extract --select '**/triggers.xml' → 0 rows   |  matchGlob('**/triggers.xml','triggers.xml')  → false
tools/bin/wad-scan extract --select 'GAMEDATA.BIN'    → 0 rows   |  matchGlob('GAMEDATA.BIN','gamedata.bin')     → false
                                                                 |  matchGlob('**/*.xml','triggers.xml')         → false
```

**A trap worth carrying forward:** with these semantics `**/name` (and even `**/*.name`) does **not** match a
flat `name` — `**` becomes `.*` but the following `/` stays literal. A glob meant to catch both flat and
nested entries must be given twice (`name,**/name`). The corpus's `gamedata.bin`/`triggers.xml` are flat, so
the plan's example works as written.

## Contradictions, judgment calls, limits

1. **`--json` renders unresolved hashes differently from the reference script.** `wad-census.mjs`'s *table*
   prints `<unresolved N>` but its *JSON* keys them `"N"`; this tool uses `<unresolved N>` in both. After
   normalising that one naming difference there are **zero count disagreements**; the counts are the same
   numbers, and the difference is a convention choice (one naming rule in one home) rather than a measurement.
2. **`ClientDump.json` "unresolved" ≠ undeserializable.** `triggers.xml`'s class hash `0x06DAAC43`
   (114,994,243) is not in `ClientDump.json` — it is hand-written in Imcodec's **server** type registry as
   `WizZoneTriggers`, which is why `extract` deserializes all 3,377 of them (`failed 0`) while the census
   prints them `<unresolved …>`. Any later story that treats the census's unresolved list as "cannot be read"
   would be wrong.
3. **Census wall clock: 28.8 s here vs the reference's 23.4 s.** Same tree, same single-threaded strategy
   (bounded 8 KB compressed prefix → 12-byte header), slower inflation path (`Ionic.Zlib` stream per entry vs
   Node's one-shot `inflateSync` with `Z_SYNC_FLUSH`). Not tuned; the census has no time budget.
4. **`BindSerializer` needs a fresh instance per entry.** It flips its own `SerializeFlags` bit when it sees
   the `BINd` magic; a reused instance then reads a 4-byte flags word from a shape-B payload's *hash* and looks
   for the class hash 4 bytes too late. The tool constructs one per row — this is load-bearing, not style.
5. **Shape B is recognised only through `--classes`.** Measured control (`census --gamedata …` with no
   `--classes`, 27.7 s):

   ```
   object entries: shape A (BINd) 176943 in 140 classes; shape B (bare) 0 in 0 classes
   object entries total: 176943 in 140 classes
   note: no --classes given — shape B (a bare class hash) cannot be recognised, so its entries are not counted.
   ```

   The 6,733 shape-B objects vanish from the total, and all 140 shape-A rows print as `<unresolved N>`
   (the name table is also what names them). The tool says so on stderr rather than guessing. Shape A needs no
   name table (`BINd` is the evidence), which is why unresolved shape-A classes still count with `--classes`.
6. **Extract's `propertyMask` is `BindSerializer`'s default (7, `Save|Copy|Public`)** — the same call
   `imcodec op file` makes — not the mask 1 `ZoneDataService` uses. The parity check above is against the CLI
   in that same configuration; no attempt was made to see whether mask 1 would drop fields.
7. **`extract` always writes one row per selected entry**, including entries that failed to deserialize (they
   carry `error` instead of `class`/`object`), so the row count is the selection's contract. On the real tree
   `failed 0`, so this path is exercised by the unit tests only.
8. **Not done here (deliberately):** no extractor or sync stage (p6-04/p6-05 own those), no committed
   verification script (the reproduction commands are the raw `wad-scan` invocations above), and no
   .NET-dependent test — the real binary is exercised only by evidence runs.
