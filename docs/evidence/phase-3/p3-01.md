## 5. AC#2 — `NullValueHandling.Ignore` semantics

Measured reality behind the rule: **320/322** corpus files carry all 36 top-level keys and express
optionality as **explicit `null`s** (`m_clientTags: null` ×320, `m_behaviors: null` ×320, …); the
other 2 are this tool's own null-stripped writes (18 keys). Both shapes parse, and neither is
normalised: `.nullish()` accepts absent *and* `null`, and no field uses `.default()`, `.catch()`
or `.transform()`. Tests assert both directions (`Object.keys(parsed)` length 1 for a minimal
`{m_questName}` document; explicit nulls still present after a parse → `JSON.stringify` →
re-parse), and that the corpus's undocumented `ReqHasEntry` fields (`m_displayName`,
`m_isQuestRegistry`) survive — the D5 reason every object is `.passthrough()`.

### Independent verification by the lead (my own implementation, not the story's test)

A throwaway harness of mine (deleted before the round closed) parsed every quest with
`QuestTemplateSchema.safeParse`, compared with a hand-written `firstDiff` and
`isDeepStrictEqual`, and collected every `$type`:

    real  : files=322 strictJson=16 parseFailures=0 distinctTypes=26 unknownTypes=0 tableSize=27
    clone : files=322 strictJson=17 parseFailures=0 distinctTypes=26 unknownTypes=0 tableSize=27
    (both: "✓ parses every quest deep-equal and knows every $type")

So **322/322 parse with the parse output deep-equal to the source on both corpora**, and no
`$type` is unknown to the table.

## 7. Deviations, judgment calls and limits

1. **`m_goalType` is an open string, `$type` is a strict literal** — accepted and recorded as
   D56(b): the corpus is ~1/12 of the game (D52(i)), so a closed enum would 400 real content.
   The 7 measured values are pinned in `GOAL_TYPE_VALUES` with a test on the set.
2. **`m_questName` is now `z.string().min(1)`** — a deliberate tightening (the spec's type).
   `m_questName: 42` used to pass through `objectKeyFromData`'s finite-number acceptance; it is
   now a 400. Nothing in the corpus or the suites sends a numeric name.
3. **One existing test expectation changed** — `quests-api.test.ts`'s save fixture built a goal
   with **no** `$type` and expected 200; with a strict union it is a 400, and a `$type`-less goal
   is precisely what Imlight cannot deserialize. The fixture gained the real
   `$type: TYPE_STRINGS.WaypointGoalTemplate` (a comment says why); no assertion was weakened and
   the 400 table gained 4 rows (57 pass where 53 did). Reviewed and accepted by the lead.
4. **Corpus-source provenance** — the fixture records the **real** path (7,956 occurrences); the
   D17 clone measures 7,911 because it carries this tool's own 2 rewritten files. Both are 26
   distinct. Strict-`JSON.parse`-able: **16/322 real, 17/322 clone**; **306 need JSON5**
   (consistent with D48(b)).
5. **My own correction**: I told the executor "all 322 files contain trailing commas". Wrong —
   306 do. Recorded in `corpus-type-inventory.txt` rather than smoothed over.
6. **`ReqIsSchool`** is in the union and `KNOWN_TYPE_STRINGS` but not `CORPUS_TYPE_STRINGS`
   (0 occurrences in quests); **`GoalCompilation` is deliberately absent** — it is Imcodec's
   intermediate `MSG_QUESTOFFER.GoalData` representation (a FixtureGen input, registered in
   Imcodec's type registry) and never a saved quest's goal class; the real CLI was run to
   confirm the reader emits the 5 real classes.
7. **Not proven / honest limits** — p3-01 ships **no serializer** (no `stringify` in
   `shared/quest/`), so the write-direction of the round-trip contract is p3-02's to prove;
   goal `$type`s outside this 322-file corpus are unmeasured (the live game is unavailable on
   this host); CI does not run the real grep (explicit skip reason, recording asserted instead);
   the spec-silent objects (`m_behaviors`, `m_missionDoors`, `m_dynaMods`,
   `m_defaultDialogAnimation`, `m_questEffectInfoList`) are preserved verbatim but unmodelled
   (all `null` in this corpus, so no shape is known).
