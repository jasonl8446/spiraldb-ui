## 3. Measured corpus reality this story rests on

The engine's whole severity model is derived from what the corpus actually does:

- **Six of the rules have ZERO corpus violations** — `m_questName` empty, dangling `m_startGoals`,
  duplicate `m_goalName`, a final logic entry that does not complete, an invalid `$type`, and a
  non-positive template id. **0 findings each across 322 real quests**, so their UI paths are
  fixture-only and are labelled as such in the engine header, the test names, the UI spec header and
  this record.
- **Reachability is real**: exactly **5 quests / 35 goals** (`WC-CYCLOPS-MAIN-002` 6,
  `WC-TRITON-MAIN-008` 4, `WC-TUT-C03-001` 19, `WC-TUT-C05-001` 5, `WC-TUT-C08-001` 1). *All five
  carry `m_startGoals: []`*, so the "no logic" reading and the "no start goals" case coincide here
  and no special case was invented.
- **Zones are real**: **94 warnings** (`m_destinationZone` 43, `m_zoneTag` 20, `m_cameraZoneName` 31,
  `m_zoneName` 0) against the 1,241-row `zones` table; every **empty string is exempt** (measured
  presence: `m_destinationZone` 423 of 773 empty, `m_cameraZoneName` 840 of 1,706, `m_zoneTag` 67 of
  194).
- **The D63(c) trap is handled**: `ResDrawHand.m_templateID` declares **both** `spells` and `npcs`,
  so the engine emits **0** reference warnings on the corpus — an NPC-only reading would emit exactly
  6 false positives against values the corpus legitimately uses (its 8 distinct ids resolve 6 in
  spells, 2 in npcs, 0 in both).
- **Two measured corrections the plan's letter needed**: "TemplateID fields positive integers" is
  literally false for **2,005** real occurrences — `m_actorTemplateID` is `0` in 330 of 1,706 dialog
  entries and `m_walkAwayNpcTemplateID` `0` in 1,675 of 1,706 (the D64(f) "0 = none" sentinel) — so
  those two declare `min 0` while `m_templateID`/`m_spellID` (42/10 occurrences, all ≥ 35,528) keep
  `min 1`; and no quest field references an item (above).

## 7. Decisions (D65, recorded in `docs/plan-overview.md`)

- **Severity follows the corpus, not the letter of L531.** The six zero-violation rules **block**;
  `goal-unreachable` and `zone-not-known` **warn**. The reason is measured: 5 of 322 **shipped**
  quests violate reachability and 94 zone values miss, and p3-05 already presents the same
  reachability finding as the flowchart's warning banner (D61) — blocking would make real,
  game-shipped content permanently unsaveable. One finding kind and one fixpoint serve both surfaces.
- **The reference tables are injected, not fetched by the engine**, and they come from the cache the
  dropdowns already fill; **an empty table counts as absent**, so an unimported database (D44's
  tier-1 harness) cannot flood a real quest with false warnings. Documented cost: the quest detail
  page now loads the five tables once per session (~43k rows).
- **`ResDrawHand.m_templateID` resolves in either table** (D63(c)), which is the difference between 0
  and 6 false positives on the corpus.
- **Sentinel `0` is not a missing id** for `m_actorTemplateID`/`m_walkAwayNpcTemplateID` (2,005 real
  occurrences), so the "positive integer" rule applies where it is meaningful and nowhere else.
- **The 3.9/3.10 seam is explicit and machine-checkable**: the Save button ships with
  `data-save-wired="false"` and one `onSave` prop for 3.10 to fill; 3.10 must **not** re-derive the
  disabled state. The header's Edit button keeps its "Editing arrives in Phase 3" behaviour.
- **One honest spec re-scope**: `quests-info-editor.spec.ts`'s page-wide "no `role=alert`" became
  Info-editor-scoped plus `m_questTitle` clean, because the shared `MOCK_QUEST` legitimately carries
  a blocking finding (`m_goalLogic[0].m_completeQuest: false`) that another spec pins deliberately.

## 9. What this story did **not** prove

- Five of the six blocking rules' UI paths are **fixture-only** (no corpus violation exists). Only
  the dangling-start-goal path — the AC's own example — was driven end-to-end live.
- The **save pipeline is not wired** (3.10): no UI POST, no toast, no dirty guard, no mode swap.
- Warnings are not returned in the server's 200 body (not asked for), and the server re-reads the
  five tables per save rather than caching them.
- Inline granularity is honest but uneven: Info/Goals/Goal Logic get per-field messages; Results and
  Dialog get per-field messages on their central controls with the id controls showing the red
  border; the requirement tree reports at node level rather than per select.
- No pixel inspection of the screenshot; 768px/mobile was not re-checked.
