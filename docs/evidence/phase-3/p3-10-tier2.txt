Subagents have no playwright-mcp, and the executor's honest limit was that its AC1 test drives the
UI's **edit builders** rather than a browser click. This pass closes that gap: the lead edited a
real quest **through the rendered UI**, saved it, and diffed the **D17 clone**.

## The rig, with D65(g) applied

`cp data/spiraldb-ui.db /tmp/p310-tier2.db` then **`DELETE FROM settings`** (the copy keeps its
settings rows and `seedSettings` only seeds an empty table, so `SPIRALDB_PATH` would otherwise be
ignored and the POST could reach the owner's real fork). `GET /api/settings` was checked **before**
any save and returned `spiraldb_path = /home/jason/Documents/git-projects/spiraldb-ui/data/test-spiraldb`
and `git_branch = content/2026-09-26`. The clone was at `18dc924`, clean, and the target file was
snapshotted to `/tmp/p310-before.json` first.

## One failure my own gate run produced, and what it means

The FIRST lead gate run reported `npm test` **1033 passed / 1 failed** — the victim was the p3-08
dialog corpus sweep (`tests/unit/quest-dialog.test.ts`, the test carrying `realFiles`), which scans
**both checkouts**. The cause was mine: my tier-2 rig was rewriting `data/test-spiraldb` at that
moment. Re-running that file alone (28 passed) and then the whole gate on a quiet clone gave
**7 × rc=0**. Recorded because it exposes a real property of this suite: **the D17 clone is shared
mutable state** — the isolation test resets it and several sweeps read it — so clone-writing and
clone-reading tests must not overlap. Vitest runs files in parallel by default, so this is a
**latent flake risk** for gate-3/CI (see D66(g)).
