## 3. Decisions (D66, recorded in `docs/plan-overview.md`)

- **Edit mode is the load state** (`EDIT_MODE_ON_LOAD = true`), with view mode one click away. The
  plan says only that the toggle "switches between view and edit mode"; defaulting to edit keeps the
  seven committed editor specs meaningful on load and matches what the product is for. Recorded as a
  choice, with the alternative (load in view mode) noted as a one-line flip if the owner prefers it.
- **View mode is literally "no panels"** — the same `renderPanel` seam, so the read-only bodies are
  p2-07's, never a second copy (D60g's generalisation paying off again).
- **The guard stops propagation as well as preventing the default**, because `<Link>` navigates
  programmatically.
- **`dirty` is a byte comparison against the baseline**, so an edit that returns a field to its
  loaded value is clean, while a moved key is dirty — the honest definition, and the reason AC3's
  "restores exactly" is provable.
- **The Wrap control is implemented, superseding the p2-07 deviation**, because the AC and the spec's
  ASCII both name it.
- **The identity gate is part of the save chain** (measured live: a rig without a user name has its
  save held while the dialog opens, and resumes after the name is saved) — the p3-10 pipeline runs
  *after* D38's gate rather than around it.

## 4. Gate, and a flake risk the lead's own run exposed

`docs/evidence/phase-3/p3-10-gate.txt`, lead-run on the frozen tree: `npm test` 42 files / **1034
tests**, `npm run test:ui` **166 passed**, lint, `typecheck:tests`, both `tsc` projects and the build
(entry 661.43 kB / gzip 199.96 kB, +4.11 kB raw / +1.39 kB gzip for this story, no new dependency).

**The first lead gate run failed one test** — the p3-08 dialog corpus sweep, which scans **both
checkouts** — and the cause was the lead's own rig rewriting `data/test-spiraldb` at that moment.
Re-running that file alone (28 passed) and the whole gate on a quiet clone gave 7 × `rc=0`. Recorded
because it exposes a property of the suite: **the D17 clone is shared mutable state** (the isolation
test resets it; several sweeps read it), so clone-writing and clone-reading tests must not overlap,
and vitest runs files in parallel by default — a **latent flake risk for gate-3/CI** (D66(g)).

## 5. Independent verification (lead-authored)

`p3-10-independent-verify.txt`, 6 checks, **6/6 green**, over all 322 corpus quests: a freshly loaded
document is never dirty; edits make it dirty; reset is **byte-exact** (deep-equal *and* stringify
equality, so key order included) and idempotent; editing a value back is clean; a key-order-only
change is dirty while `documentsEqual` correctly reports byte-inequality; and saving advances the
baseline so a saved document is clean.

**Three of my assertions failed on first runs and every one was mine** (recorded in that file):
`editQuestDocument` takes an **array** of edits; the shared primitives refuse to invent an
intermediate element (so my sweep had to edit only existing paths); and `documentsEqual` is
byte-level **by design**, so my "ignores key order" expectation was wrong.

## 7. What this story did **not** prove

- **Browser Back/Forward is not intercepted**: `useBlocker`/`usePrompt` need a data router and the
  app uses a plain `<BrowserRouter>`; a popstate hack would desync the router for every route. It
  needs a shell decision and is recorded rather than faked.
- `beforeunload` was asserted by synthetic dispatch, not a real window close.
- The server's 400 `fields` map is not rendered inline: `ApiError` carries no body, so the client
  engine blocks first and the toast carries the server's message. Flagged, not faked.
- `EDIT_DISABLED_TOOLTIP` ("Editing arrives in Phase 3") now describes only the browse table's
  still-disabled row Edit action — stale copy plus a dead affordance, left because p2-08's spec pins
  it; a Phase-5 candidate.
- The AC1 automated test drives the UI's edit builders rather than a browser click — the lead's
  tier-2 pass closed that gap for one quest, not for every path.
- No pixel inspection of the screenshot; 768px/mobile was not re-checked.
